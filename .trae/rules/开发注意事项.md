## 0. ★ 函数注释规范（置顶，新写/修改函数必看）★

所有 **用户函数**（项目自写函数）的注释统一下列 **Doxygen 格式**；**新增函数必须用此格式**，**已有函数注释逐步改成此格式**（模板参考下面、及第 10 节）。

模板（`@brief` 一句话概括，换行对齐续写补充；`@param 名称 说明` 每个参数一行且名称对齐；有返回值才写 `@return`；踩过的坑才写 `@note`）：

```c
/**
* @brief  只重绘单个数字格（选中格=高亮底+数字，未选中格=框底色+数字）。
*         用于 增加/下一位 局部刷新：不动边框/文字/整框，避免整框重画闪烁。
* @param  it       含数字拼接片段项（如 page4_texts[0]）
* @param  cursor   当前选中位（1~digit_count）
* @param  cell_idx 要重绘的数字格下标（0=第1位, 1=第2位, 2=第3位…）
*/
```

注意：注释为中文，`@brief/@param/@return/@note` 行对齐；参数名称对齐。

> [!WARNING]
> **编码坑**：源文件为 GBK，加/改中文注释必须用 GBK 脚本（`io.open(..., encoding='gbk')`），禁用 SearchReplace/Edit 直接写中文（会写坏成 `?`，见第 14 节）。

**代码整理规范（改任何文件前先看，配合第0节）**：
- 用户函数一律 Doxygen（见上），`*/` 后直接贴函数、**不要空行**；一个函数只保留一个注释块，**删除**多余/错位的旧说明（可并入 `@note`）。
- 宏 `#define`、`static const` 数组等**定义统一置顶**（放在本文件顶部常量区），并加中文行内注释；**不要散落在函数中间**（如 `D2048_SAVE_LEN` 移到顶部 `D2048_DEBUG` 旁并注释字节组成）。
- **删除**框式分节标题（`/* ===== */`），函数用 Doxygen 即可；常量组可保留一行中文注释。
- include 注释用中文（描述用途），不写符号名（如 `GAME_RET_*`），写成中文（如“游戏返回码”）。
- 函数之间保留一个空行；`*/` 与函数之间**不要**空行。
- 函数定义**不要写单行**（如 `static uint16_t tile_x(uint8_t col) { return ...; }`），即使只有一个 return 也要拆成标准多行写法（函数体 `{}` 各自独占一行）。

## 2. 模式切换（config.h）

三模式宏，**同一时间只能开一个**：
- `FLASH_DATA_STORE_MODE` — 字库/图片烧录到外部 Flash
- `VIDEO_CHUNK_STORE_MODE` — 视频块烧录
- 都不定义 — 正常游戏/视频播放

切换用脚本，会同步改 config.h 和 makefile：
```
powershell -File "BIN文件烧录器\switch_mode.ps1" burn   # 烧录模式
powershell -File "BIN文件烧录器\switch_mode.ps1" game   # 游戏模式
powershell -File "BIN文件烧录器\switch_mode.ps1"        # 查看当前
```

## 3. 编译下载

- **两模式都不加 `-flto`**（flto 在游戏模式致 sokoban.c 链接失败 `R_RISCV_RVC_BRANCH`，超大函数分支超范围）
- MRS 每次编译会重新生成 makefile 恢复 flto，**烧录用命令行不用 MRS**
- 一键编译下载（工程根目录）：
  ```
  powershell -File 编译与下载.ps1          # 编译+下载
  powershell -File 编译与下载.ps1 build     # 仅编译
  powershell -File 编译与下载.ps1 flash     # 仅下载（elf 已编好）
  powershell -File 编译与下载.ps1 clean     # 清理重编+下载
  ```
- **编译策略（2026-09 已改为"增量优先，失败再清"）**：`编译与下载.ps1` 的 `Do-Build` **不再每次编译前清空 `.o/.d/.map/.lst`**，而是**先 `make all` 增量编译**（快）；仅当增量编译**失败**（如源码转码后旧 `.o` 调试信息失配导致的 `invalid string offset` 链接错，或 GCC 内部报错如 `verify_flow_info failed`）才**清理 `.o/.d/.map/.lst` 后重编一次**。既恢复增量速度，又保留对"旧 `.o` 调试信息失配"的兜底。若增量偶发 GCC ICE，清理重编多为正常。
> [!WARNING]
> **PowerShell -Include 坑（踩过）**：`Get-ChildItem -Path $dir -Recurse -Include *.o,*.d` 在 `-Path` 传目录（非通配符）时 **`-Include` 不生效、匹配不到任何文件**，导致清理无效、仍报链接错。必须改用 `-Recurse -File | Where-Object { $_.Extension -in ... }` 才可靠。
- SWD 连不上 `WCH-Link failed to connect with riscvchip` 多半是设备休眠/没电，充电唤醒后 `flash` 重下

**关于 `-flto` 与 obj/*.mk（重要踩坑）**：
- **`-flto` 不只出现在主 makefile，还出现在各 `obj/**/subdir.mk` 的编译命令里**：编译出的 `.o` 是 LTO 目标，链接器会自动做 LTO 优化，照样触发 `R_RISCV_BRANCH` 超大函数分支超范围。因此要删就**所有 obj/**.mk 一起删**（`-flto` 字符串逐一确认，别漏）。
- **这些 `obj/**/*.mk` 是 GBK 无 BOM 编码**（注释为中文）。删 flto/改路径时**严禁**用 `PowerShell [IO.File]::ReadAllText(.., UTC8)` 全文本读改写，否则中文目录名（彩屏/源代码/大屏幕 - 触摸屏）会变 `锟斤拷` 乱码，导致 include 路径错误、`fatal error: xxx.h: No such file or directory`。要用 `[Text.Encoding]::GetEncoding(936)` 读、写回 GBK，或用字节级操作（**不要用编辑工具 SearchReplace/Write，见下条**）。
- **用编辑工具（SearchReplace/Write）改 `obj/makefile`、`obj/**/*.mk` 会把中文路径整片写成 `????`（2026-09 踩过）**：工具按系统 ANSI 写回，像 `...\10.SA-250514(彩屏)\...\大屏幕 - 触摸屏\SRC\Ld\Link.ld` 这样的路径会变成 `...\10.SA-250514(????)\...\?????\...\SRC\Ld\Link.ld`，链接随即报 `cannot open linker script ... Link.ld: No such file or directory`（或找不到 `.o`）。
  - **症状识别**：链接报"找不到 Link.ld / .o"时，**第一步先看 `obj\makefile` 里的路径是不是 `????`**，不要先怀疑工具链 —— 本次曾把它误判成"ld 调试信息 bug（`invalid string offset`）"，围绕 strip-debug 白折腾了好几轮。
  - **修复**：从同目录**未损坏**的文件（如其它 `subdir.mk`）里取正确规则行覆盖回去；改完用 `Select-String "\?\?\?\?"` 确认 `????` 已清零。
  - **预防**：`obj/**/*.mk`、`obj/makefile` 只用 PowerShell 按 GBK 读改写；若不得已用了编辑工具，改完**立刻**检查 `????`。
- **工程根目录名含空格**（`0.SOLO-AI eyes-源代码`、`大屏幕 - 触摸屏`）：make 的**规则依赖中的无引号绝对路径**会被空格截断，报 `No rule to make target '.../0.SOLO-AI'`。位于工程根 `SRC/` 的子目录（Core/Debug/Peripheral/Startup）源在 `.mk` 里用的是无引号绝对路径，需改成相对路径 `../../../SRC/...`（make 在 obj 目录运行，obj→SPI_LCD→SPI→工程根）。而 `-I".../SRC/Debug"` 这类**带引号**路径 make 会经 shell 处理、能容忍空格，可保留。

**空片/换新板出厂全量烧录（顺序：字库 → 视频 → 程序；2026-09 实践验证）**：

| 步 | 内容 | 落在哪 | 做法 |
|----|------|--------|------|
| 1 | 字库/图片（`s_resources[]`，实测 **65 项**、约 58KB） | 外部 Flash **末尾** | 打开 `config.h` 的 `FLASH_DATA_STORE_MODE` → 跑 `编译与下载.ps1`（编译+烧写）→ 设备复位后自动执行 `FlashStore_BurnAll()`；**结果用 SWD 回读 `g_res_prog` 自动判定**（`result=1` 全部通过 / `=2` 有 CRC 失败，详见下面条目） |
| 2 | 视频（`压缩数据1~4.bin`，57 块） | 外部 Flash **地址 0** | 把关掉的字库宏确认注释 → `switch_mode.ps1 burn` → `burn_all.ps1 -start 0`（约 3 分 45 秒，逐块 SWD 回读校验） |
| 3 | 游戏程序 | MCU 内部 Flash | `switch_mode.ps1 game` → `编译与下载.ps1`（GAME 固件 64908B/99.43%） |

- ★ **三个模式宏只能有一个生效**：字库宏与视频宏同时定义时，main.c 的 `#if/#elif` 只会走视频那条，但字库的 58KB 资源数组**仍会被编进来**（可能撑爆 Flash）→ 每次切模式都要确认另一个是注释状态。
- **字库烧录的回读握手 `g_res_prog`（2026-09 新增，取代"人眼看屏幕 100%"）**：`flash_store.c` 的 `FLASH_DATA_STORE_MODE` 段里定义
  `volatile res_prog_t g_res_prog` = `{ magic='RES1'(0x52455331), total, index(从1起), pct, crc_fail, result(0=未完成/1=通过/2=有失败) }`，6 个字连续，一次 `mem2array` 读完；
  PC 端流程照搬 `burn_all.ps1` 那套：`nm` 取 `g_res_prog` 地址 → `openocd … -c "mem2array m 32 0x<addr> 6" -c 'echo RP=$m(0),$m(1),…' -c shutdown` → 正则解析 → ★**先校验 magic 再信字段**（MCU 刚复位时 RAM 是随机/编程残留，会冒充"烧完了"）。
  实测：`pct=11 index=13/65 crc_fail=0 result=0`（烧录中）→ `pct=100 index=65/65 crc_fail=0 result=1`（全部通过）；加这套后固件 58316→58412B（89.48%）。
- 字库模式烧完是 `while(1)` 常驻、背光不灭、**不进待机** → 第 1、2 步之间 SWD 一直活着，**不用唤醒设备**；只有"跑着游戏固件闲置"时才需要点屏幕唤醒（§18）。
- 第 1 步写完前**别断电/复位**（写一半会留下错位资源，表面看不出来）；第 2 步期间也别手动复位（触发"83% 跳回 0"那个坑）。
- 换成**新触摸 IC（IT7259 屏）**时：第 3 步之前先把 `touch.h` 的 `TOUCH_IC_IT7259` 改成 1，否则触摸完全不工作（旧屏 CST816S 保持 0）。
- 判定"哪一步没过"的看板：第 1 步看屏幕进度条是否停在 100%；第 2 步看 `obj/burn_log.txt` 里本次运行块（`==== burn_all(patch) start=... ====` 之后）有无 `FAIL/MISMATCH/TIMEOUT`；第 3 步看 `编译与下载.ps1` 的"烧录成功"。

**批量烧板一键脚本 `BIN文件烧录器\burn_factory.ps1`（2026-09 新增，实测一块板 466s 全程无人值守）**：

- 用法：`powershell -File burn_factory.ps1 [-Boards N] [-Refresh] [-BinPath 路径] [-ProjPath 目录]`（`-Boards N` 时每块板之间停下来等你换板）
- **首次运行编译并缓存**"字库固件"与"游戏固件"到 `BIN文件烧录器\cache\`，之后每块板都是**纯烧写**：省掉每块板 2 次 `make clean` + 完整重编（约 3 分钟）。视频的基准镜像仍由 `burn_all.ps1` 自己编（run 内只编一次）。
- ★ **缓存判据用"源码内容指纹"（MD5），不能用 mtime**：脚本自己切模式会改 `config.h`、`gen_video_chunk.py` 每块都重写 `video_chunk.c/h` —— 用 mtime 会把每次运行都误判成"源码变了"而白重编一遍（真踩过）。指纹里排除 `video_chunk.*`，并把 `config.h` 的两个模式宏**归一化**（切模式不算改动）；源码真变了自动重编，要强制重编加 `-Refresh`。
- ★ **缓存固件身份自检**（`Assert-Sym`）：字库固件**必须含 `g_res_prog`**，游戏固件**绝不许有 `g_res_prog`**（它是 `#ifdef FLASH_DATA_STORE_MODE` 里的符号，天然是两者的判别标志），两者都不许有 `g_video_chunk`（游戏模式里被 `--gc-sections` 回收）。
  - 2026-09 真踩过一次，且原自检没拦住：**"游戏固件"编译前忘了关字库宏** → 编出来的"游戏固件"其实是字库固件（两份大小都是 61,696B 时最迷惑，因为只看 `g_video_chunk` 两边都没有）。结论：**关字库宏必须在编译之前**，判别标志要用 `g_res_prog`。
- ★ **烧字库固件时先 halt、`mww <magic 地址> 0` 再 `reset run`**：不这么做，PC 会读到上一次/上一块板留在 RAM 里的 `result`（和本次一模一样）而冒充"烧完了"。
- 三步 SWD 全自动重试（200 次 × ~3.3s ≈ 11 分钟窗口）；每块板在 `obj\factory_log.txt` 记一行 `board N OK/FAIL <秒数>`。
- 两个收尾动作**无论走哪条分支都要执行**：① 字库宏关回去（只有编译阶段会开它，"游戏缓存命中"时容易漏 → `config.h` 会停在字库模式）；② `config.h` 停在"视频烧录模式"（`burn_all.ps1` 要用它编基准镜像）。脚本结束后会再恢复成 GAME。
- **批量省事技巧**：给板子**插着充电线** —— 充电时设备不进待机、SWD 一直活着，全程不用点屏幕（§18）。

**视频数据块烧录流水线（`BIN文件烧录器\burn_all.ps1`）+ SWD 回读握手（2026-09 新增；脚本 2026-09 从 `数据\娜娜莉\` 移入工程 `BIN文件烧录器\`，三个脚本都已改成"位置无关"）**：
- 用法：`powershell -File burn_all.ps1 [-start N] [-count N] [-BinPath 路径] [-ProjPath 工程目录] [-SettleMs N] [-SwdSpeed KHz]`
  - **脚本放哪都行（2026-09 改）**：工程根 = 从脚本所在目录**向上**找含 `SPI\SPI_LCD\User\src` 的目录；找不到再扫 `..\..\源代码\*`（针对"脚本放在工程外原位置 数据\娜娜莉"的情况）；`-ProjPath` 可显式指定。`gen_video_chunk.py` 用同一套逻辑。
  - **源视频 .bin 可指定路径**：`-BinPath` 优先；不填则依次找 脚本目录 → 工程内 `数据\娜娜莉` → 外层 `数据\娜娜莉`，都没有就报错提示用 `-BinPath`。生成器同理支持 `python gen_video_chunk.py <块号> [raw] [--bin <路径>]`。
- 每块流程（当前快模式）= `python gen_video_chunk.py N raw` 只产出原始数据+CRC（不重编）→ 按符号地址贴进基准镜像副本 → openocd SWD 烧 MCU（MCU 上电再把 `g_video_chunk` 写进外部 Flash），块大小 53248B；旧的"每块 `gen_video_chunk.py N` + `make all`（放在后台作业里并行）"是早期做法，已被上面的快模式取代
- **握手（★不要再用"猜一个固定等待时间"）**：烧录固件把进度写进全局结构 `g_burn_prog`（`flash_store.c`，仅 `VIDEO_CHUNK_STORE_MODE` 编译）——
  `magic`(`BURN_PROG_MAGIC`='BURN')/`index`(块号)/`stage`(0擦除 1写入 2回读校验 3结束)/`pct`(0~100)/`crc_src`/`crc_rd`/`result`(0=没烧完 1=通过 2=失败)/三段耗时 ms；
  结构体保证 10 个字连续，PC 端 `nm SPI_LCD.elf` 查 `g_burn_prog` 地址后，**一次 `mem2array ... 10`** 全部读回，读到 `result != 0` 才进下一块。
  ★ **magic 必须放结构最前面、且是固件最先写的一个字段**：MCU 刚复位、`.bss` 还没清零时读到的可能是**编程时留在 RAM 里的缓冲残留**（固定不变的垃圾值），
  不校验 magic 就会把垃圾当"烧完了"（踩过：报出 `stage=2607631256` 这种鬼数字）。
- **为什么必须握手**：下一块烧录前的 `program ... reset` 会复位 MCU；若上一块**还没烧完就被复位**，
  最后约 1 个扇区(4KB)就写不进去。屏幕表现是**"进度条烧到 83% 忽然跳回 0"**
  （83% ≈ 写入阶段第 12/13 个 4KB 块，写入阶段占进度条 10%~90%）。
  这种被截断的块**不会出现红色进度条**（根本走不到回读校验那一步），只能靠握手或重烧发现
- 实测每块耗时：`-SettleMs 2000` → 4.6s（勉强够，但靠猜，慢一点的块就可能被截断）；`500` → 3.5s、`300` → 3.3s（★会截断，别用）；握手 + 去掉固定等待 → **4.0s/块**
- **"不每块重编"已经做了（2026-09，burn_all.ps1 现在的快模式）**：run 开始 `python gen_video_chunk.py <start>` + `make all` 得到**基准镜像**（整个 run 只编译这一次）；
  每块只跑 `python gen_video_chunk.py <i> raw`（只产出 `obj/chunk_meta.bin` 24B + `obj/chunk_data.bin` 53248B，**不重编**），
  再按"符号地址 → 所在段的文件偏移"（`nm` + `objdump -h`）把这两段贴进基准镜像的副本 `obj/burn_patch.elf` 烧掉。
  能这么做的前提：生成器把每块参数（偏移/长度/块号/CRC）放进 `g_chunk_meta[]`，`video_chunk.h` 的宏改成读这个 `extern const volatile` 数组
  （跨编译单元 + volatile，编译器不会把它折叠成常量）；数据数组定宽 `VIDEO_CHUNK_MAX_SIZE`=53248（末块补 0xFF），保证每块生成的文件形状一致、补丁偏移才稳。
- **★ 但这个"快模式"并不会更快（实测，别再重复踩）**：`python raw` 只要 **0.03s**；每块 4.0s 的真实构成是
  **openocd program 会话 2.57s**（61KB 内部 Flash）+ 回读会话 0.61s + 杂项。
  之前"天花板是编译"的判断是错的：编译一直跑在**后台作业**里、与烧录重叠，从不在关键路径上。
  要再提速只能动 program 会话本身，但两条路都试过、收益都很小：
  · 把数据数组 `__attribute__((aligned(4096)))` 后只写那 53KB：写量只从 61.4KB 降到 57.3KB（省 6.5%，因为写量主体就是 53KB 数据本身）≈ 0.13s/块，
    而且对齐填充要吃掉仅剩的 ~4KB Flash 余量（当前 61352/65536）—— **不值得做**；
  · `riscv set_prefer_sba on` + 字节宽度回读：**新会话里能读到真值**（`0x4e,0x52,0x55,0x42,0x37` = magic 'BURN' + 块号 55，且不用停核），
    但 `program` 之后同一会话里读仍是垃圾（换访问方式也没用）→ "一个会话跑完烧录+回读"这条路彻底死掉。
  ? **实测地板 ≈ 4.0s/块**（program 2.57s + 回读 0.61s + 杂项），全片 57 块约 3.8 分钟。
- **快模式的端到端校验（★别省）**：`gen_video_chunk.py` 的 raw 模式会打印 `CRC=0x....`（与固件同一个 MODBUS CRC16），
  脚本拿它跟握手回传的 `index` + `crc_src` 比对，不一致立刻停。实测把期望值故意 +1 → 日志出 `CRC MISMATCH ... 已停` ?。
  不做这一步的话，补丁贴错位置/基镜像过期都会"自校验通过"（固件拿自己镜像里的数据自比，必然相等）。
- **踩坑（PowerShell 侧）**：`[Text.Encoding]::UTF8.GetString(bytes)` 读带 BOM 的脚本会**保留** U+FEFF，
  再用 `UTF8Encoding($true)` 写回就成**双 BOM** → 运行时报 `param(...)` 处"赋值表达式无效"（和 obj/*.mk 那个双 BOM 同类）。
  改完脚本要 `TrimStart([char]0xFEFF)` 并检查前 4 字节是不是只剩一个 `EF BB BF`。
- **"烧录 + 轮询塞进同一个 openocd 会话"不可行（试过）**：`program {elf} reset` 之后在**同一个会话**里读 RAM，
  读到的是**固定不变的垃圾值**（编程时留在 RAM 的缓冲残留，不是外设/时序问题），halt 后读也一样；
  只能分成两个会话做（多花一次 openocd 启动 ~0.7s）
- **不要在"把擦除换成 64KB 块擦除/预擦除"上花功夫**：实测这颗 W25Q64 的扇区擦除只要 **13.5ms/4KB**
  （13 个扇区 175ms，比手册典型 45ms 快得多），换块擦最多省 ~100ms/块（~2%），
  却要背上"块擦会连带擦掉同一 64KB 块里已烧好的数据"的风险，不划算
- **openocd/SWD 两个坑（都踩过）**：
  - `mem2array` 的地址**必须带 `0x`**：写成 `mem2array m 32 20000020 1` 会被当**十进制**解析成 `0x1312d14` 这类野地址，
    报 `Failed to read memory` 后 openocd 直接退出（退出码非 0）
  - `echo` **只能给一个参数**：`echo A=$x B=$y` 会让 openocd 报错退出。多个值要拼成一个参数，如 `echo BP=$m(0),$m(1)`

## 4. 字库/图片资源（外部 Flash）

- 资源通过 flash_store.c 的 `s_resources[]` 表烧录到外部 W25Q64（8MB）
- **改字库/图片大小，必须同步 `s_resources` 对应项的 size**，否则后续所有资源偏移错位
- 资源读取用 DMA（`flash_store_read` → `SPI1_Read_DMA`），不要改成阻塞读
- **关卡地图已搬到外部 Flash（2026-09）**：50 张地图（`sokoban_maps.c`，Bcd 压缩约 2.7KB）不再是 `static`，改由
  `s_resources[]` **末尾 50 项**登记成资源 65~114（`FLASH_STORE_ID_SOK_MAP_0 + 关卡序号`）；顺序 = `sok_map1..50` = `sokoban_levels[0..49]`，**三处必须同序**。
  - 游戏模式：选关时用 `FlashStore_ResRead` 把该关 BCD 读进 `sokoban.c` 的 128 字节 RAM 缓冲 `g_level_bcd`（长度按 `ceil(rows*cols/2)`），再解压进 `g_runtime_map`；同一关重复进入不重读（`s_bcd_level` 记着）
  - 收益：游戏固件 Flash **64,908 → 62,160 B（99.43% → 95.22%，余量 372 → 3,120 B）**；代价：RAM +744B（外部 Flash 目录缓冲随资源数 +600）、字库烧录固件 58,412 → 61,696 B（94.51%）
  - ★ 资源表一变，**每块板子都必须重烧"字库/图片"那一步**（`burn_factory.ps1` 会自动带上新表）
  - ★ 头文件里地图只能声明成"不完整类型"（`extern const uint8_t sok_mapN[]`）→ **编译期 sizeof 不出来**，
    所以这 50 项的长度编译期先填 0，由 `FlashStore_BurnAll` 开头按 `rows*cols/2` **运行期补上**（也正因要写它，`s_resources[]` 去掉了 `const`）
  - 没烧新字库的旧板子：推箱子会画成**空白关卡**（读失败时故意填 `0x66` 外界格），其它功能照常 —— 一眼能看出是漏烧
  - ★★ **长按连跳切关慢：实测结论（2026-09，在 sokoban.c 里挂 `volatile` 计时器，再用 openocd `mem2array` 读 RAM 量出来的）**
    改前：一次切关 **103ms**（其中地图重绘 **90ms**），正常帧只有 4.6ms；改后：切关 **60ms**、重绘 **47ms**，逐次间隔稳定在 **117~145ms**（贴着 `HOLD_REPEAT_US`=130ms 的节拍，无尖刺 = 长按没被误判松手）。
    原因按大小排：
    1. **每格都从外部 Flash 读"调色板+图"**（`sok_load_pal_img`，约 1.1KB/格；一关 ~200 格 ≈ **400 次 SPI 读 / 230KB**）——这正是"加外部 Flash 之后才变慢"的主因。
       改法：`sokoban_draw_level` 改成**按图块类型分趟画**（`sok_draw_pass`：底色→墙→箱子→箱子在目标上→目标点→玩家），**一张图一次重绘只读一次** → 每关 **~420 次降到 7 次**（6.3KB）。
       对照：外部 Flash 迁移前（`git show eac9b01` 之前）是直接指针读内部 Flash 的 const 数组，零 SPI 开销，所以差别很明显。
       ★ 透明精灵（目标点 `0x0000`、玩家 `0xffff`）必须后画，且保持"先目标点、后玩家"的层次；前 4 趟不透明且格子互不重叠，先后无所谓。
       ★ 逐格的 `sokoban_draw_cell_at` 保留给"单格重绘"（移动/局部刷新）用，别删。
    2. **清屏用逐像素的 `LCD_Fill`**：240×240 = 57,600 像素，每像素 4~5 次标志轮询 + GPIO 写（约 0.9?s）≈ **50ms**，是最大值。
       改法：换 `LCD_Fill_DMA`（先填 5120B 模式缓冲再 DMA 循环发，末尾等 BSY，仍是同步的）→ 约 **14ms**。★ 除清屏外别用异步的 `LCD_Clear`（会与后续绘制竞争留残留）。
    3. **CH32V203 没有硬件除法**（`/`、`%` 走 `__udivsi3`，几十上百周期）：`sok_draw_scaled_tile` 原先**每像素**算一次 `(c*30)/g_tile_size`（一关 ~80 格 × 900 像素 ≈ 25~50ms）；
       改成"每次重绘只算一张 30 项列映射表、其余查表"（+64B Flash）。
    → **热循环里绝不放除法**（按像素/按格跑的都要查表），**也别按格去读外部 Flash**：几百次 SPI 读同样致命。
  - 节拍与耗时的关系：`HOLD_REPEAT_US`=130ms 是**下限节拍**，只有"切关耗时明显小于它"才稳；一旦重绘接近或超过它，就会一帧塞不下、看起来"时快时慢"。给切关加动画/加绘制前，先量这个值（挂 `volatile uint32_t` 计时 + openocd 读，见上面的做法）。
- 字体位序统一 **MSB-first**（字节高位 = 最左像素）
- 关卡数字字体 16×32 红色

**RGB565 图片资源约定（大鱼吃小鱼即此）**：
- **字节序必须小端序**（`uint16_t` 按低字节在前存），否则 LCD 上 RGB565 红蓝颠倒。现有 `sok_img_next.h` 等图标均标注"小端序"
- **透明色用 `0xFFFF` 白色**（不是黑色 0x0000！），绘制函数跳过白色像素。参考 `sok_nav_draw_rgb565` 但透明判断是 `==0xFFFF`
- **共用绘制函数按 level 参数化**：`draw_image_sprite(id_base, dims, count, level, x, y)`，用 `FlashStore_ResLoad(id_base+level, 0, w*h*2)` 流式读入 scratch 后强转 `(uint16_t*)` 绘制。玩家和小鱼分两套图：
  - 玩家：`FLASH_STORE_ID_PLAYER_0` + `player_imgs_dim`（`玩家.txt`，9张 20×16→52×41，成长等级 0-8，吃小鱼逐级长大）
  - 场上小鱼：`FLASH_STORE_ID_FISH_0` + `fish_imgs_dim`（`鱼图片.txt`，10张 16×12→52×31，等级 0-9）
- **scratch 缓冲区必须 ≥ 最大资源字节**：最大为玩家 52×41×2=4264，`FLASH_STORE_SCRATCH_SIZE` 已扩到 **4352**（当前 RAM 约 78%）。改资源后记得核对
- **生成脚本**：`gen_fish_imgs.py`（鱼图片.txt）与 `gen_player_imgs.py`（玩家.txt），输出 `.c` 到 font_library、`.h` 到 Game/inc（头文件必须在 include 路径 Game/inc）
- 只改字库/图片资源后，需用烧录模式（FLASH_DATA_STORE_MODE）重新烧写外部 Flash，游戏模式才能读到新资源

## 5. 内部 Flash 存档

- 存档区 `0x0800FF00~0x0800FFFF`（单页轮换，防写入中断损坏）
- **链接脚本 Flash 长度必须 `0xFE00`**（不能 0x10000，会覆盖存档区）
- 仅 CRC 变化时才擦写（减寿命损耗，相同内容跳过）
- 存档含：魔数/版本/序号/长度/CRC16，**最大 256 字节**
- 俄罗斯方块棋盘按每格 3bit 压缩；推箱子只存关卡+人物+箱子位置
- 存档加载后需完整重绘游戏画面

## 6. 休眠唤醒

- 无触摸 10 秒 → 关背光 → LCD/触摸/Flash 休眠（RAM 与画面保留）
- `KEEP_LCD_POWER_IN_STANDBY` 必须开（触摸唤醒的前提）
- PA8 EXTI Event 唤醒后做**软件复位**（完整重初始化 LCD，避免状态残留）
- 用 `PWR_EnterSTANDBYMode_RAM()` 不是 `PWR_EnterSTANDBYMode()`（保栈有效）
- CST816S 进休眠前写 `0xF5=32` 调灵敏度，唤醒后 `Touch_Init()` 重置 + `0xFE=1` 禁自动休眠
- 唤醒后第一帧触摸隔离，连续两帧确认松开才允许游戏操作
- 休眠前 `IWDG_Disable()`，唤醒后 `IWDG_Init()` 恢复 ~1 秒看门狗
- 休眠期间 TIM1 运行用于低电检测，不再用于喂狗
- 华容道计时扣除休眠时间；俄罗斯方块逻辑休眠期间停止

## 8. LCD 绘制

- `LCD_Fill` 填到 Y=239 需传 `(x, y, 240, 240)`（内部 xend/yend 减 1）
- **菜单条带渲染已改为乒乓双缓冲**（`menu_draw_nrow_frame_only()` 内）：复用 `shared_buffer` 前后两半（`STRIP_H=8` × `ROW_BYTES≤300` = 2400B/块，两块共 4800B ≤ FILL_BUFFER_SIZE），**0 额外 RAM** 恢复"画/发流水线并行"。**别再加独立的 `s_menu_strip_buf1`**（会白耗 5120B RAM，且已删除）
- 方案对比：菜单条带**单缓冲**（每条带串行等 DMA）会导致下滑菜单变卡；**双缓冲**（画下一块时上一块在 DMA 发）才流畅。RGB 播放/游戏共用 `shared_buffer`，菜单与它们串行调用不会冲突
- 全屏清黑用**同步** `LCD_Fill(0,0,LCD_W,LCD_H,LCD_BLACK)`，不要用异步 `LCD_Clear()`（会与后续绘制竞争导致残留）
- ★ **大块纯色填充改用 `LCD_Fill_DMA(x1,y1,x2,y2,color)`**：逐像素 `LCD_Fill` 每像素约 0.9?s（4~5 次标志轮询+GPIO 写），240×240 要 **~50ms**；
  `LCD_Fill_DMA` 把 5120B 模式缓冲填好后 DMA 循环发，末尾等 BSY（同步），同样一屏约 **14ms**（有效吞吐 2.3MB/s → 8.2MB/s，快约 3.5 倍）。
  推箱子切关清屏已换（重绘 90ms→47ms）。注意它内部自己管 CS，且会占用 `shared_buffer`，别与进行中的 DMA 绘制并发
- 菜单背景用 `MENU_BG_COLOR`（LCD_CYAN）避免黑闪
- 菜单坐标钳位到 `[0, 239]` 防 `uint16_t` 溢出
- **RAM 警戒线**：工程 RAM 只有 20KB，`bss`+`data` 一度到 90.9%；当前约 79%。新增常驻大数组/缓冲前先权衡，能走外部 Flash 流式就不要常驻 RAM
- **增量绘制防重叠残留**：透明图增量擦除某实体旧矩形（`clear_entity_rect` 背景填充它的包围盒）会误伤与其重叠的其他实体像素，留下"被啃一块"的缺口。可靠做法：填背景后**立即按固定顺序重绘该矩形内所有相交实体**（用当前坐标），一次性正确恢复，避免跨帧标记/连锁残留。参考 fish.c
- **主循环无帧率控制**：`while(1)` 全速空转，未按下（无触摸 I2C 负载）时帧率远高于按下时。凡是"每 N 帧移动一次"的动画在未按下时会疯狂加速。**改用真实时间节拍**（`GetTimerCount()` 返回微秒；如鱼每 40ms 移动一次），与帧率无关；随机速度要保证不全为 0，避免鱼停死
- **游戏结束画面**：屏幕中央"游戏结束"（32×32 红字，`FLASH_STORE_ID_32_YOU/XI3/JIE/SHU`）+ 下方"重新开始"提示（24×24 白字，`FLASH_STORE_ID_24_CHONG/XIN/KAI/SHI3`）；点击任意位置重开
- **LCD 片选(CS)陷阱**：`LCD_Fill`/`LCD_Clear` 内部会自己 `LCD_CS_CLR/SET`。凡是**不带 CS 控制的绘制函数**（如 `sok_draw_digit_scaled`/`sok_draw_char_32`）若紧跟一次 `LCD_Fill` 之后调用，此刻 CS 已被置为无效，数据写不进显存 → 该内容"消失不见"。**在 `LCD_Fill` 之后、用这类函数绘制前务必先 `LCD_CS_CLR`**。反之 `LCD_Fill` 自己会重设 CS，接在后面无碍。
- **菜单清除已改 DMA**：`LCD_CLEAR_MENU_AREA()`/`LCD_CLEAR_RESTART_AREA()` 用 `LCD_Fill_DMA`（同步，函数内 `while(BSY)` 等发送完，**非 `LCD_Clear` 那种异步**，不会与后续绘制残留；用共享 `shared_buffer`，`FastFill_16bit_Repeat` 会把长度钳到 `FILL_BUFFER_SIZE` 防溢出）。`menu_clear_exit_area_to` 仍用同步 `LCD_Fill`。全屏清黑仍用同步 `LCD_Fill`。注意：引用 `LCD_Fill_DMA` 会使 Flash 增大（约 +0.8%，当前 94.23%，余量约 3.7KB）。
- **菜单清除色可配置（避免切菜单黑闪）**：`LCD_CLEAR_MENU_AREA()`/`LCD_CLEAR_RESTART_AREA()`/`menu_clear_exit_area_to` 现在用全局 `g_menu_clear_color`（默认 `LCD_BLACK`）。游戏可设为自己背景色（如 fish.c `fish_init` 里 `g_menu_clear_color = COLOR_BG`），清菜单位置直接填背景色，比"清黑+重绘"更快、无黑闪；其它游戏保持黑色。`game_handle_ret` 在**模式切换（换游戏/视频）时重置为黑色**，避免泄漏到其它游戏；进设置（EXIT_RET_SETTINGS）不重置（回同一游戏）。
- **设置页/二级设置菜单返回防黑闪**：从游戏进设置（`menu_enter_game_settings` 打开 `g_video_menu_row_types` 的二级设置选项菜单）点“返回”回游戏，走 `GameSettings_Update` 的 else 分支。原来先 `LCD_Fill(0,0,LCD_W,LCD_H,LCD_BLACK)` 整屏刷黑、再 `*_full_redraw()` 延迟到下一帧才重绘 → 黑闪。**应只清二级菜单条带**（`LCD_Fill_DMA(VIDEO_MENU_X, VIDEO_MENU_Y, VIDEO_MENU_X+VIDEO_MENU_W, 240, g_menu_clear_color)`，用 `g_menu_clear_color` 背景色），再**同帧** `*_full_redraw()`+`*_update()` 恢复场景。二级菜单是底部覆盖条、场景始终在它后面，无需整屏刷黑。返回键在触摸释放帧触发（`ts.pressed==0`），此时直接调 `*_update()` 只重绘、不误触手势，是安全的。此段代码所有游戏共用（下划设置菜单、三级设置页返回都是同一分支）。
- **菜单背景重绘要尊重进菜单前的状态**：俄罗斯方块游戏结束后上滑/下滑菜单，背景应显示“游戏结束”画面而非棋盘。菜单状态里的背景重绘用 `g_state_before_menu == TETRIS_STATE_OVER` 分流——是结束就画“游戏结束”，否则画棋盘。**切莫把触发条件写成恒真**（如 `g_board_dirty >= 2 || g_state_before_menu == TETRIS_STATE_OVER`），因为进菜单前是结束时该条件恒为真，会在菜单状态下每帧重画背景（含外部 Flash 读“游戏结束”字库），与菜单渲染反复互相覆盖 → 闪屏。应沿用 `if (g_board_dirty >= 2)` 只触发一次，内部再分流。
- **圆形屏 240×240**：顶部圆弧窄，顶部信息/文字须**水平居中**放进圆弧可见带（y 越往下越宽），切勿贴左右角；四角默认在圆外不可见，实体可游动区用**8角形**（矩形四角倒角 `PLAY_CORNER`），且角落要加**角落反弹**（`fish_bounce_corners`）反转速度，否则鱼会卡角很久不动。

## 12. 大鱼吃小鱼（fish.c）

- **玩法**：触摸**增量拖动**控制玩家大鱼（按住滑动时按手指位移增量平移，刚按下记录起点不动，松开停，不吸附到手指）；碰同级/更小 吃掉成长，碰更大 失败；结束后点击任意处重开。玩家物理初始等级 0（第1条沙丁鱼形象）。玩家/小鱼**按游动方向左右翻转**（`facing`：0=右、1=左）。
- **左右转向**：`draw_image_sprite` 新增 `flip` 参数做**水平镜像**绘制（flip=1 时非透明段起点左移、像素倒序）；`FishEntity.facing` 存朝向（0=右、1=左）。玩家按拖动 `dx` 定朝向（`dx<0` 向左），小鱼按 `vx` 定朝向（`vx<0` 向左）。**所有实体绘制（含 `clear_entity_rect`/`fish_move_redraw` 内部重绘相切实体）都要传 `facing`**，否则转向后残影/方向错乱。
- **得分/升级（分数制）**：吃 `N` 级鱼得分 = `5^N`（`fish_thresh`：0级=1分、1级=5、2级=25…）；累计分 ≥ `5^(level+1)` 就升一级（`g_score` 为 `uint32_t`）。HUD 显示等级 = **物理等级 + 1**（方便判断升级了几次）。
- **通关（1,953,125 分）**：达到 `FISH_WIN_SCORE=1953125`（显示10级）即**通关**，设 `g_won=1`＋`g_state=FISH_STATE_OVER`，画面中央画绿色"通关"两字（`FLASH_STORE_ID_32_TONG/GUAN`）；玩家最大等级封顶**物理9级=显示10级**（`FISH_PLAYER_LEVEL_MAX=9`）。玩家等级 ≥ `FISH_PLAYER_LEVEL_MAX-1` 时**可吃到大白鲨（等级+1 的鱼）**，从而能累计到通关分。
- **玩家形象/尺寸封顶**：`PLAYER_IMG_LVL` 把玩家等级封顶到最大图片（`PLAYER_COUNT-1`），避免物理 `level=9` 超出图片范围导致"玩家消失"；`draw_image_sprite` 里 `level>=count` 也钳位用最大一张。**所有用到玩家等级的地方**（碰撞半径、清矩形尺寸、绘制）都要用 `PLAYER_IMG_LVL`。
- **HUD（圆形屏）**：两行。行1=分数（居中，黄色），行2=升级进度条 + 当前等级（居中，等级紧贴进度条右侧，白色）；数字用 `sok_draw_digit_scaled`（7x11 或 8x14），用 `g_hud_dirty` 脏标记变化才重绘。进度条按"当前级分数占比"填 10 格。**等级 ≥ 10 须画两位数字**（先画"1"再画个位，布局宽度 `pl_total` 相应按 2 位加宽），否则 `sok_draw_digit_scaled(...,10,...)` 越界不显示。
- **可游动区 & 卡角**：`fish_clamp_pos`（矩形钳位 + 四角倒角成 8角形）用于玩家/生成点；小鱼移动后还要 `fish_bounce_corners`（角落斜边速度反弹）防卡角。`PLAY_TOP` 控制游戏区上界（信息栏底 + 1px），`PLAY_CORNER` 控制倒角大小。
- **透明判定**：`IS_TRANSPARENT(p)` 接近白色（R≥0x1C/G≥0x38/B≥0x1C）即透明，替代仅 `==0xFFFF`，避免边缘残留。
> [!WARNING]
> **注意坑（踩过，改代码前先看）**：
  - **食物等级分布必须"大部分吃到"**：曾用"玩家±3"分布，开局只有 0 级可吃 → 玩家吃不到鱼、无法成长。现改为 75% 等级 0..玩家级（可吃）、25% 玩家级+1..+2（挑战）。`FISH_FOOD_RANGE` 宏已废弃，勿再沿用。
  - **吃掉鱼"先更新新位置、再擦旧图"**：`food_respawn` 须先设好新的 `x/y/level`，再用**旧的** `prev_x/prev_y/prev_level` 调 `clear_entity_rect`（清旧矩形；其内部重绘相交实体用的是已更新的当前坐标）。顺序颠倒会把新位置画回旧矩形背景。

  - **玩家碰撞半径是近似值**：`pr = 8 + level*4`，不是用图片实际宽高做碰撞；等级越高越快，需与图片尺寸匹配，避免"看起来没碰到却吃了/败了"。

## 14. 编码坑：SearchReplace 会写坏 GBK 中文（2026-09 新增）

- **坑**：用 `SearchReplace`/Edit 工具编辑 GBK 源文件的**中文注释**时，工具会把中文写坏成 ASCII `?`（如注释变 `????`）；或把 GBK 字节当 UTF-8 解码后再写回，导致整文件中文变 `?`、且再转 GBK 也救不回（内容丢失，非单纯编码问题）。
- **规避**：要往 GBK 文件加中文，**一律用 PowerShell `[Text.Encoding]::GetEncoding(936)` 读/写**，别用 SearchReplace 写中文；只改 ASCII/代码可用 SearchReplace；若文件已 `?`-化且非 git 管理（如 `.trae/rules/*.md`），只能靠**备份覆盖 + 重加**，务必先存好每日备份。
- **发现**：菜单反向手势/视频设置页这批改动时，`menu.h/menu.c/tetris.c/sokoban.c/d2048.c/klotski.c` 及 `.trae/rules/开发注意事项.md` 中文注释被 `?`-化；恢复方式=`git checkout`(git 文件) / 每日备份覆盖 + 重加(规则文件)。
> [!WARNING]
> **转UTF-8判据（2026-09）**：转码前先剥离注释再用正则检测**代码里的中文字符串字面量**（`"[^"]*[一-?]..."`），**有才不能转**（如`语音IC`、`显示中文字`这类被代码引用的中文串）。**更正**：`User/src/touch.c` 此前误判为含中文字符串字面量、严禁转，实测其中文全在注释里（`CN_literal=no`），**可以安全转 UTF-8**，已转。
> **已全部转 UTF-8（2026-09 完成）**：`User/inc/*.h`（15个，9个 GBK→UTF-8 + 6个原已 UTF-8）、`User/src/*.c`（14个，12个 GBK→UTF-8 + 2个原已 UTF-8）。`LCD/src/lcd.c`、`LCD/src/spi.c`、`LCD/src/flash.c` 也已转并规范注释。凡已转 UTF-8 的文件，编辑中文可直接写（不再受 GBK 坑影响）；仍为 GBK 的文件继续走 GBK 脚本。
- **经验补充（2026-09，decompress.c 视频闪烁注释改中文）**：① **任何中文只要出现在命令行里（PowerShell 命令 / `python -c "..."`）就会被 trae-sandbox 破坏成 `?`**，即使脚本逻辑对也没用；② Write 工具写出的中文文件实测是 **GBK 编码**（"启用"= `0xC6 0xF4 0xD3 0xC3`），不是 UTF-8，用 `UTF8Encoding` 读会乱码、用 `gbk` 读才对；③ **可靠做法 = 全 ASCII 的 Python 脚本**：路径用 `os.getcwd()` 相对拼接（源码不含中文路径字节），脚本内 `io.open(..., encoding='gbk')` 读写，中文内容放 GBK 临时文件里由脚本读；全程中文不出现在命令行，GBK 读写一致不坏；④ Write 工具能写 GB2312/GBK（GBK 是 GB2312 超集，收 6763 常用字之外的扩展字），但"能写 GBK"≠"能直接把中文搬进 GBK 源文件"，关键瓶颈是命令行破坏中文，所以仍需脚本搬运。

  - **再次发生（2026-09，"语言设置"功能）**：`chinese_fonts.c/.h`、`menu.c/.h`、`settings.c/.h` 6 个文件被写回 GBK（`flash_store.*`、`main.c` 侥幸没中）。按上面流程 GBK→UTF-8 转回**文本无损**；校验办法：核心代码没变、`?` 的数量增量应只来自新增代码里的三目运算符。

## 18. WCH-LinkE 休眠设备无法烧录：OpenOCD 连接复位无效（2026-09）

**现象**：设备进入 Standby（PA8 触摸唤醒，见 §6）后，用 `编译与下载.ps1` 烧录报 `WCH-Link failed to connect with riscvchip`。

**试过且无效**：OpenOCD `reset_config srst_only srst_nogate connect_assert_srst` + `init`/`reset halt` 的"连接时复位唤醒"。报错在 `WCH-LinkE mode:RV`（适配器初始化）后立刻出现。

**原因**：WCH-LinkE 驱动要先跟芯片完成自身的 **SDI 握手**，这一步发生在 OpenOCD 能施加复位**之前**；芯片在 Standby 时两线调试口已关闭（WCH 手册：用户程序**开了休眠**/把**调试脚复用为 GPIO**，调试口失效），驱动握手必然失败。故 OpenOCD 对 WCH-LinkE 的 connect-under-reset **无效**，属于驱动层面限制，非接线问题（RST 接没接都一样）。

**可靠唤醒后烧录的办法**（选定：保持物理唤醒现状，不改代码）：
- **进 BOOT 模式(ISP)**：BOOT0=VCC、BOOT1=GND → 芯片进 bootloader（不跑会待机的用户程序）→ SWD/ISP 可连，烧完恢复 BOOT0=GND。WCH 官方对"程序开休眠/占调试脚"的标准做法。
- **手动复位时机**：按住板子 RESET（拉低），点烧录，等 WCH-Link 开始握手时**松开**，让芯片在复位后、跑待机前被抓住。
- **物理唤醒**：充电（PB6 充电唤醒）或点一下屏幕（PA8 触摸唤醒），设备醒来后再 flash。
- 开发期也可用 `DEBUG_NO_STANDBY` 编译（设备不睡，烧录随时能连），但烧的是不待机固件，不能用于测休眠。

## 22. IT7259 新触摸 IC 接入（2026-09）

新触摸屏 TK0128F25K 用的是 **ITE IT7259**（旧屏是 CST816S），两者**接线完全相同**（RST=PB8 / INT=PA8 / SCL=PB10 / SDA=PB11），靠 `touch.h` 的 `TOUCH_IC_IT7259` 宏切换（**1=IT7259 新 / 0=CST816S 旧**），寄存器/命令差异全部收在该宏的 `#if` 分支内。

**官方手册**：`5.资料\1.28寸触摸屏TK0128F25K整理资料\IT7259+User+Programming+Guide_V0.11.pdf`（ITE 官方编程手册，**含全部命令与数据格式**）。同目录 `IT7259_V0 2_20160720.pdf` 只有硬件规格，**没有寄存器表**。

### 22.1 通信协议（与 CST816S 完全不同：Command + 缓冲区模型）

I2C 地址 **0x46**（手册 3.1.1 "1000 110"），数据格式**小端**。芯片提供 4 读 4 写缓冲区，用 **3 位缓冲区索引**寻址：

| 缓冲区 | 地址(索引) | 属性 | 用途 |
|---|---|---|---|
| Command Buffer | `0x20`(001b) | 只写 | 下发命令 `[命令, 子命令/长度, 参数...]` |
| Query Buffer | `0x80`(100b) | 只读 | **必须先读它**判状态 |
| Command Response Buffer | `0xA0`(101b) | 只读 | 命令执行结果 |
| Point Information Buffer | `0xE0`(111b) | 只读 | 点数据报告（14 字节） |

- **Query Buffer(0x80) 语义**（手册 4.3.1）：bit7-6 = 包信息状态 → `1xb` **有新数据包** / `01b` **无新包但手指仍按着** / `00b` 无手指；bit1-0 = 命令状态（`00b`=Done、`01b`=Busy、`10b`=Error）。
- **读点必须"先查 Query 再读点缓冲区"**（手册 4.1：无论中断还是轮询，都要先取 Query 状态）。**跳过 0x80 直接读 0xE0，芯片不推进读指针 → 一直取到旧包 → 表现为"移动很长坐标才更新"**。
- **点数据报告**（0xE0 起 14 字节）：Byte0[7:4]=Format Tag(**0000b**)、[3]=Finger、[2:0]=Point Information（**0=所有手指离开**）；`X = ((Byte3 & 0x0F) << 8) | Byte2`；`Y = ((Byte3 >> 4) << 8) | Byte4`；Byte5=Pressure（0=无接触/1=悬停/2=轻触/4=正常/8=重按/Fh=重压）。
- **手势报告**：Format Tag = **1000b**（首字节 0x80），只含手势 ID/起终点/方向、**不含当前坐标** —— **绝不能把它当成"无点/抬手"**，否则长按时会断触。

### 22.2 关键命令（写 `[命令, 子命令, 参数]` 到 0x20）

| 命令 | 参数含义 |
|---|---|
| `{0x15, 0x1D, n}` | **Point Threshold**：`移动距离 > resolution × n / 1000` 才上报该点（**默认值大 → 滑动时坐标一格一格跳**，如 118→129；本项目设 0） |
| `{0x15, 0x18, n}` | **Engine Scan Period**：引擎扫描周期，单位 ms（本项目 5ms） |
| `{0x15, 0x06, n}` | **Report the Last Point**：bit0=1 输出最后一点，bit7-1=**跳过范围**（**非 0 也会造成台阶**，本项目 0x01） |
| `{0x15, 0x88, 4×n}` | Smooth Algorithm Factor：Byte0/1=Smooth Distance Strong/Weak，Byte2/3=Smooth Alpha Strong/Weak |
| `{0x04, 0x00, 0x01/0x00}` | **Set Power Mode**：参数 `0x01`=Idle（25uA，**不上报任何包、也不接受命令**，触摸才唤醒）、`0x00`=Active（1.5mA） |

命令是否被接受：回读 Query Buffer 的 **bit1-0**（`00b`=Done）。

> **坐标"一格一格跳"的根因就是 `Point Threshold` 与 `Report the Last Point` 的跳过范围**，与刷新率、每帧读取次数、读长度都无关（这几个方向本项目已逐一排除）。

### 22.3 软件滤波（`touch.c` `Touch_TryApplyCoords`，仅 IT7259 分支）

阈值调小后静止时会抖，故叠加两级滤波：
- **3 点中值滤波**（`Touch_Mid3`）：丢掉静止时的**孤立大幅跳动**；慢速滑动只延迟 1 帧、输出真实采样值，**不产生台阶**。
- **死区 1px**（`TOUCH_IT7259_DEAD_ZONE`）：X/Y 变化都小于死区就沿用上次坐标。
  > **不要设 3 及以上**：死区是"与上次坐标比、小于就沿用"，在**拖动等跟手场景**里会把小位移吃掉、变成**固定量化台阶** —— 实测设 3 时菜单拖动"每 3 像素动一下"。防抖请交给上面的中值滤波（它输出真实采样值、不产生台阶）。

另外 IT7259 分支的**跳变过滤阈值放宽到 300**（原 80 会把连续采样成片丢弃，也表现为"移动很长才更新"）。

### 22.4 休眠唤醒（易踩坑）

- **STANDBY 下 MCU 的 GPIO 全部高阻** → RST(PB8) 失驱动掉低 → IT7259 实际处于复位态（波形可实测）；**但 INT 仍能在触摸时给出下降沿** → 唤醒照常触发（**不需要给 RST 加上拉**，加了只是让待机时芯片保持工作、更费电）。
- 唤醒后 `Touch_WakeResumeInit()` 对 IT7259 **补一次复位（低 100us → 高）+ 等 100ms** 让 IC 就绪。
- **不能用严格的"触摸确认"**（`Main_ConfirmTouchWake` 要求连续 2 次读到按下）：实测"点一下"时 INT 只低 **7.7ms**，而确认窗口在复位+100ms 之后 → **必然错过** → 判无效 → `NVIC_SystemReset()` 回待机（**现象：点屏幕不亮**）。IT7259 直接认定有效（INT 来自触摸 IC，可信）。
- **不能让它进深睡眠**：手册 7 章"RST 低脉冲 **>1ms** 进 sleep（0.1uA）"是**彻底停机、INT 不再动作** → 点了唤不醒。IT7259 分支**待机前不睡**（保持工作、靠 INT 唤醒 MCU）；复位脉宽用 **100us（必须 <1ms）**。
- 唤醒后无需额外命令（复位后即为 Active 态）。

### 22.5 硬件与调试

- **I2C 必须加上拉**：没加时 I2C 全程 NACK（波形上能看到 `AW: 8C` 但无 ACK），加上即正常。
- **调试显示** `TOUCH_DEBUG_SHOW`（touch.h）：屏**左侧竖带**（x 11~35、y 60~186、行距 14）显示 **10 行** —— 行1 按下标志 / 行2 Byte0 / 行3 Byte2(原始X低字节) / 行4 Byte3 / 行5 Byte4(原始Y低字节) / 行6 映射X / 行7 映射Y / 行8 CSEL min / 行9 CSEL max / 行10 读取成功标志（细节见 §27.6）。
  - **圆形屏四角在圆外不可见**，必须放在左中部/左侧竖带（距圆心 <120）；`sok_draw_digit_scaled` 前要 `LCD_CS_CLR`（见 §8）。
  - **曾压在菜单文字上导致"菜单没字"** —— 位置必须在菜单框（x=45~195）之外，现取左侧竖带即为此。
  - **正式版本要关掉**（`TOUCH_DEBUG_SHOW 0`），能省几百字节 Flash。
- **Flash 余量**：本工程 Flash 上限 **65280B**，正式版常年在**几十字节**量级（如 76B）；开调试显示约 250B、去掉内容闪烁改动后约 188B。动代码前先看余量，不够时可先用 §27.6 的黑屏调试版（整块编译掉视频解压，可省约 2656B）腾挪。

## 23. 菜单判定区与手势门控（2026-09，已修）

换触摸 IC 后暴露的几个菜单问题。**都不是触摸 IC 的问题**，而是菜单自身的判定区/门控，已按下述方式修好（`menu.c`/`menu.h`/`main.c`）。

### 23.1 最后一行点不中 / 点它下面反而返回

- **判定区**：`menu_hit_test()` 用固定 5 行几何（`MENU_Y=5`/`MENU_H=230`/`MENU_BDR=5`）算行号，最后一行只覆盖 **186~229**；而菜单框下沿画到 **235**、圆屏最下方 y 能到 **239** → **230~239 整段被判成"菜单框外"**。
- **两种菜单的判定方式不同（关键）**：
  - **主菜单**用**按下那一帧**的坐标（`main_menu_handle(ts.x, s_touch_start_y, …)`）→ 松开坐标漂移不影响；
  - **游戏退出菜单**要求 `pressed_hit == released_hit`（`game_exit_menu_poll`）→ **松开坐标漂出框外就完全不响应**。
- **修法**：
  1. `menu_hit_test()` **不再按菜单框下沿截断**：只要 x 在菜单宽度内，y 从框顶到 239 都**夹到最近的行**（最后一行实测 186~239）；只有"点在菜单框上方 / 左右外侧"才返回 `-1`。
  2. `game_exit_menu_poll()` 加兜底：**松开坐标向下漂出框外、且 x 仍在菜单宽度内**时，以**按下那一行**为准（最后一行紧贴屏幕下沿，抬手瞬间接触面向下滑出，坐标常落到框外）。拖到菜单左右侧外松手仍按原语义取消。
- **副作用**：菜单宽度内点最下方不再能"点空白关闭"，关闭请点菜单框**左右两侧**（x<45 或 x≥195，圆屏上仍有可见可点区域）。

> ★ 本节修的是"框边到屏幕最下沿掉空"，但**行与行之间**的分界线仍与画出来的行不一致（见 **§30**）。现在行归属统一走 `menu_row_from_y()`，本节结论仍有效（夹到最近行），只是实现换了。

> 改判定区/行高时必须**一并核对"手指实际能碰到的范围"**：圆屏越靠下，可见可点区域越窄（只剩中间一小段），不能只看菜单框画到哪。

### 23.2 下滑菜单时上划菜单也弹出来（拖动过程中弹出）

- **根因**：`game_menu_command()` 退出菜单分支里"底部上划 → 切上划(重开)菜单"（`menu_swipe_to_restart_handler` → `game_menu_swipe_up_poll`）**在退出菜单拖拽/滑入期间也判定**。下滑打开退出菜单时手指停在屏幕下方（y > `y_threshold`），上划检测会把**起手点重录在那片区域**（该函数在 `!g_touch_down` 时会重录 `g_touch_start_y`），之后几像素上漂（抬手/噪声）就满足 `dy < -5` → 上划菜单被抢出来；而退出菜单的滑入动画（3px/帧、约 1.3s）还在继续 → **两个菜单同时出现**。
- **修法**：① 该分支加 `!g_exit_dragging && !g_exit_sliding` 门控（与旁边"中间区域上划关闭退出菜单"的写法保持一致）；② 退出菜单**滑入结束那一帧若手指仍按着**，补 `g_menu_cooldown = 15` 吸收这次刚落下的触摸。
- **相关**：从主菜单点进游戏时手指常还按在屏上（菜单项在中下部，正落在"上划重开菜单"起手区）→ `main_run_game()` 首次初始化时置 `g_menu_cooldown = 30`。

> 共用全局手势状态（`g_touch_down`/`g_touch_start_y`/`g_menu_cooldown`/`g_exit_*`/`g_restart_*`）在**界面切换时必须一并考虑**：菜单态切换期间若手指仍按着，起手点会被重录成"手指当前所在区域"，极易把另一个手势误触发。

## 24. 跟手拖动：指数平滑 + "最大滞后"上限（2026-09，已修）

**场景**：跟手拖动（大鱼吃小鱼、亮度条、下滑菜单、主菜单拖动）原先统一用"每帧向目标靠近固定比例"的指数平滑（位置每帧靠近 1/3，或菜单每帧最多走 N 像素）来压静止抖动。问题是**快速滑动时整个滑动可能只有一两帧就走完**，按 1/3 迭代只能到 1/3、5/9… **累计约一半**；而拖动只在按住时执行，一松手就停在半路（不会自己补完）。

> **实测现象**："快速滑动很长距离，鱼只移动大概一半；慢慢移动就没问题。" 与触摸采样率、丢包无关，是**设计上的跟随限速**。

**修法**：小位移仍走原平滑（手抖幅度就在这个量级内，去抖效果不变），再加一条**最大滞后**上限：与目标的距离超过 `LAG` 时，**超出部分直接走掉**，只保留 `LAG` 的滞后。

```c
int16_t step = diff / SMOOTH_DIV;          /* 原平滑: 小幅抖动吃掉 */
if (diff >  LAG) step = (int16_t)(diff - LAG);   /* 大位移: 只保留 LAG 的滞后 */
else if (diff < -LAG) step = (int16_t)(diff + LAG);
```

| 位置 | 文件/函数 | 原平滑 | 最大滞后 |
|---|---|---|---|
| 大鱼吃小鱼拖动 | `fish.c` `fish_update_drag` | `FISH_SMOOTH_DIV 3` | `FISH_MAX_LAG 8` |
| 亮度条 | `settings.c` `Brightness_Update` | `BR_SMOOTH_DIV 3` | `BR_MAX_LAG 8` |
| 游戏退出菜单拖动 | `menu.c` `game_menu_drag_poll` | 单帧 `MENU_DRAG_MAX_STEP 4` | `MENU_DRAG_MAX_LAG 12` |
| 视频下滑主菜单拖动 | `main.c` `Main_HandleTouchInput` | 单帧 `MENU_DRAG_MAX_STEP 4` | `MENU_DRAG_MAX_LAG 12` |

> **尚未改**的两处同款限速（手感不足时照此加"最大滞后"即可）：`RESTART_MENU_DRAG_MAX_STEP 3`（上划"重新开始"菜单）、`VIDEO_MENU_DRAG_MAX_STEP 4`（视频上滑"设置"菜单）。
> 调参方向：滞后小 = 更跟手但手抖更易透出；滞后大 = 更稳但快滑会留相应像素的差距。
> 顺带：鱼的位置跟得更紧后，转向判定（读鱼自身平滑位移）也更灵敏了。

## 25. 设置页下滑进退出菜单：背景必须"整屏重绘"（2026-09，已修）

从游戏进设置后，顶部下滑（起点 y < 40）会切到该游戏的退出菜单。**设置页是整屏画上去的**，这条路 `main.c` 会先把屏幕刷黑（`LCD_Fill(0,0,LCD_W,LCD_H,LCD_BLACK)`；若只是二级条带可见则只清条带区），所以**换回游戏画面时必须是"整屏重绘"**。

## 26. 四方向触摸归一化：翻转后"边缘判定带"够不到（2026-09，已修）

**现象**：屏幕翻转 90°/270° 后，**上划/下滑菜单都很难滑出来**（"要很下面滑才行"），而且**左右不一样**（左侧好划、右侧难划）。

**根因**（`touch.c`）：
- 换方向时唯一变的是 `MADCTL(0x36)`（`lcd.c` 里 `0x08/0x68/0xC8/0xA8`）。**四个 case 的旋转映射本身是对的**（`0x68→(my,239-mx)`、`0xC8→(239-mx,239-my)`、`0xA8→(239-my,mx)`），点击是准的，别去改它。
- 问题在：翻转后 **UI 的 Y 是由原始 X 推出来的**（`case1: 239-mx`、`case3: mx`）。而这块屏**手指实际能到的原始 X 大约是 10~230**（圆屏边缘 + 手指接触面），**跨度只有 ~220**，却要映射到 UI 的 0~239。于是：
  - 翻转后"屏幕最下"那一端永远够不到 → 上划菜单（要求起点 `y>210/220`）的判定带被压缩；
  - 两端够不到的量不同（左 ~10、右 ~10 但相对 239 更远）→ **左右判定带宽度不一样**，右边更难划。

**修法**：在 `MapCoord()` 里对两个轴统一做线性归一化（仅 IT7259 分支）——
`[TOUCH_NORM_MIN, TOUCH_NORM_MAX] → 0~239`，**倍率由窗口自动算**：

```c
if (raw < TOUCH_NORM_MIN) raw = TOUCH_NORM_MIN;
if (raw > TOUCH_NORM_MAX) raw = TOUCH_NORM_MAX;
mapped = (uint32_t)(raw - TOUCH_NORM_MIN) * 239 / (TOUCH_NORM_MAX - TOUCH_NORM_MIN);
```

> **踩过的坑：改 `MAX` 必须让倍率跟着变。** 曾用固定移位近似（按 239 档算 ×1.047），
> 结果单独把 `MAX` 改成 210 时输出最大只到 208，而底部上划要求 `y>210` → **那条带子直接被关掉**，
> 表现为"改了反而更难划"。现已改为按窗口自动算倍率，两个宏才是纯粹的旋钮。

**调参口诀**（当前实测确认值见 §27.5：**X 20~212、Y 0~239**，X/Y 已分开标定；Y 取满量程使倍率正好 1.000、慢拖无步进）：
- 右边难划 / 右侧点不到 → **`MAX` 减小**（把判定带和右端搬到面板内侧、信号强的区域）；
- 改完左边变难划 → `MAX` 加回（两端是此消彼长的）；
- `MAX` 太小的代价：倍率变大（靠边位置失真最多约 20px），且超过 `MAX` 的最外圈变成"位置不再变化"的粘区；
- `MIN` 同理管左端。

> 想彻底不动坐标、只放宽判定阈值也能做（零失真），但比较散落在 menu.c / main.c / 推箱子 / 俄罗斯方块各自的触摸代码里（约 15~25 处），且吃 Flash。

## §27 IT7259 信号链配置与"参考地浮空"（2026-09 实测确认）

### 27.1 必须下发增益（否则"非常不灵敏"）
- `0x15/0x07` Gain Setting（1 字节）：bit7-4 = FW CDC Compensation、bit3-2 = **AFE Gain @AC Shielding Mode（放桌上/浮空）**、bit1-0 = **AFE Gain @Ground Mode（拿在手里）**，各 0~3 越大越灵敏。
- 本项目 `0x0F`（两档都最高）。**实测：把这条命令关掉（不下发）→ "触摸非常不灵敏"** => 芯片**默认增益对本屏偏低**，这条是灵敏度的命门，**必须保留**。
- 宏：`touch.h` 的 `CST816S_IT7259_GAIN_EN`（必须 1）/ `CST816S_IT7259_GAIN`。

### 27.2 轻触不稳 → 前端滤波 + 引擎模式
- `0x1A/0x02` 模拟前端滤波系数：`0x00`默认 / `0x03`=96pt / `0x05`=160pt / `0x06`=192pt / `0x08`=256pt / `0x0A`=320pt（越大越平滑、响应略慢）。本项目 `0x03`。
- `0x1A/0x04` 引擎控制：`0x03`=切**接地模式**（拿在手里）/ `0x04`=切**屏蔽模式**（放桌上）。本项目 `0x03`。
- 效果：**轻触时"按下标志"不再乱跳、且不误触**（这两条 + 27.1 的增益一起才到位）。宏：`CST816S_IT7259_AFE_FILTER` / `CST816S_IT7259_ENGINE_MODE`。

### 27.3 基线（CSEL）诊断怎么读 —— 结论：与轻触/漂移无关
- 命令 `0x1A/0x05`，参数 `0x00`=当前模式 / `0x01`=接地模式 / `0x02`=屏蔽模式 CSEL；返回 **28 个 WORD**，小端：**低字节 = CSEL、高字节 = CIN(通道号)**，从 **Command Response Buffer(0xA0)** 读 56 字节。
- 实现：`touch.c` 的 `Touch_DebugReadBaseline()`（仅无触摸时读、限流 0.5s）。调试显示行 8/9/10 = CSEL min / max / 读取成功标志。
- **实测 CSEL = 0~42，且"拿着/放下"不变** => 基线正常、不随握持漂移 => 轻触不灵与坐标漂移**都不是基线问题**，别再往这个方向查。

### 27.4 参考地浮空（本次最重要的硬件结论）
症状三连：**① 拿着与放桌上量程不同（原始 X 20~211 vs 0~239）；② 一只手触摸、另一只手靠近屏幕，X 就变；③ 屏幕右侧偏钝。**
- 原因：面板/整机**参考地浮空**，人体靠近即改变耦合 => **硬件问题，软件只能标定、不能根治**。
- 硬件对策（按性价比）：① 面板背面屏蔽层 / FPC 地线可靠接板地；② **给手指留一块"真地"**（外壳或 PCB 上接地金属片/导电泡棉，手握时能碰到）；③ 背光与触摸的地回流分开、触摸 IC 就近 0.1uF+1~10uF 去耦。

### 27.5 X/Y 分开标定（手持设备必须按"手持状态"标定）
- `MapCoord(raw, is_y)` 按轴取窗口；宏 `TOUCH_NORM_MIN/MAX_X`、`TOUCH_NORM_MIN/MAX_Y`，**倍率按窗口自动算**（见 §26 的坑）。
- 实测：原始 X 拿手里 **20~211**、放桌上 0~239；原始 Y（下发增益之后）稳定约 10~239 ? 现取 **X 20~212（×1.24）、Y 0~239（×**1.000**，严格 1:1）**。
- **Y 用满量程还有个额外好处**：倍率正好 1.000 ? **慢速拖动时严格 1px 跟随，没有"1px、2px 交替"的步进感**；X 因为要收窄窗口（×1.24），沿 X 的慢拖必然有 1?2px 节奏 —— 等硬件把参考地做好、X 也能回到 0~239 时才会消失（见 §27.4）。
- 若按"放桌上"的 0~239 标定 X，正常手持使用时右端会够不到（右侧菜单难划/点不到）。

## 29. 界面全英文（中英双语可切换，2026-09）

### 29.1 字模：两套拉丁字，各压成 1 个资源

- `FLASH_STORE_ID_LATIN24` = 29 个 14×24 半宽字（48B/字，共 1392B），菜单行用
  - 每个字模固定 24 行 × 2 字节，但**只用高 14 位**（低 2 位恒 0），绘制步进 `LATIN24_W = 14` → 相邻字不重叠
- `FLASH_STORE_ID_LATIN32` = 18 个 16×32 半宽字（64B/字，共 1152B），通关/结束/关卡大字用
- ★ **整组一个资源、按偏移取单字**（`FlashStore_ResRead(LATIN24, i*48, buf, 48)` / `FlashStore_ResLoad(LATIN32, i*64, 64)`）：若每字一个资源，资源数 +45 → 目录 RAM +540B；整组只要 +2 项（+24B）。代价是**资源表里看不出单个字**，改字必须整组重生成
- ★ **拉丁字模是按"用到的词"逐字生成的**（`gen_latin2.py` 的 `MENU_WORDS` / `WIN_WORDS`），**缺字母不报错**——只是那个字不显示、后面的字往前挪一点点，看着像"没居中"（`Tetris`/`Klotski` 曾因缺 **T**/**K** 而整体左移）。**加词必须先把词补进 `MENU_WORDS` 再重生成 + 重烧字库**，生成后用 `check_latin.py` 核对字母齐不齐
- 两个 ASCII→索引表 `g_latin24_idx[128]` / `g_latin32_idx[128]`：**定义必须放在 .c 里、头文件只放 `extern`** —— 写成头文件里的 `static const` 会让每个 include 它的 .c 各生成一份（实测 +1336B Flash ??）
- 索引 0 = 空格（全零字模，画出来自然留白）

  2. V 的斜笔**必须 2px**：1px 比其它字母 3-4px 的笔画细太多，用户会直接说"中间的 V 太细"

## 30. 菜单触摸判定：必须和"画出来的行"用同一套几何（2026-09，已修）

**症状**：
1. 游戏里上划出"重新开始 / 设置 / 返回"3 行菜单，**点"设置"经常被判成"返回"**；
2. 二级菜单（上划的设置选项条带）**滑一下再松开就进了设置页**。

**根因 1：判定区与绘制用了两套几何**

- 绘制（`menu_draw_nrow_frame_only`）：`row_gap = (mh - 2*mb - n*32) / (n+1)`，第 i 行文字顶 = `mb + gap + i*(32+gap)`（**行距里含间隙**）
- 旧判定（`menu_hit_test` 等）：把框内高（`mh - 2*mb`）**平均分**成 n 份
- 两者**分界线不一致**：n=5 时最后一条分界线比视觉中线低 **12px**、n=3 时差 4~6px → 点"返回"上半截被算成上一行、点倒数第二行下沿被算成下一行。用户体感就是"点 A 跳到 B"。

**修法：新增 `menu_row_from_y(y_top, y, n_rows)`（`menu.c` / 声明在 `menu.h`）**

- 与绘制**同一套公式**：`gap = (mh - 2*mb - n*32)/(n+1)`、`base = mb + gap/2`、步距 `32+gap`
  → 行边界正好落在**相邻两行文字的视觉中线**上，触摸区**连续无缝隙**（点在行间空隙一定归属最近的那一行）
- `y < y_top`（框上方）才返回 `-1`（点空白关闭）；框内上/下边框带、框顶到屏幕最下 y=239 都夹到最近行
- `menu_hit_test(x,y,n)` 退化成"x 范围判断 + `menu_row_from_y(MENU_Y,y,n)`"
- 调用点：主菜单 / 游戏退出菜单（5 行，`menu_hit_test`）、游戏内 3 行菜单（`menu.c` 点选重菜）、视频页与游戏内二级菜单 5 行（`main.c`）

**同时把 3 行菜单框加高**：`RESTART_MENU_H` / `VIDEO_MENU_H` **130 → 160**（行距 45px、命中区 50px，触摸容错从 ±4px 提到 ±9px）。★ **这两个宏必须一致**：3 行菜单**画框**用 `VIDEO_MENU_*`、**命中**用 `RESTART_MENU_*`。

**根因 2（滑动被当成点击）**：二级菜单原来只用**松手位置** `ts.y` 归行 → 手指在条带上滑一下、松手落在"亮度/语言"那行就直接进设置页。

- ★ **全项目统一约定：按下行 == 松手行才算"点击"**（主菜单取按下位置给 `main_menu_handle`；游戏菜单 `ph`/`ch`；退出菜单 `pressed_hit == released_hit`）
- 二级菜单按此改：`pr = menu_row_from_y(..., s_touch_start_y, 5)`、`rl = menu_row_from_y(..., ts.y, 5)`，不相等就**整帧不处理**（条带保持显示，手势也不外泄给视频/游戏）
- 行值取**按下位置**（滑动时松手坐标会漂），与"取按下行"的约定一致

## 31. 从"设置页"返回游戏必须整屏恢复（2026-09，已修）

**症状**：游戏里 上划二级菜单 → 点"语言设置"进语言页 → 再上划 → 点"返回"，屏上**留下一个绿色小方块**。

**根因**：
- 设置页是**整屏**绘制的（每页都 `LCD_Fill(0,0,LCD_W,LCD_H,LCD_BLACK)` + 内容）；
- 语言页的"当前语言"标记方块画在 `LG_MARK_X=28`（x 28~40，**在二级菜单条带 x=45~195 之外**）；
- 而退出时只按"二级菜单条带区"清屏（历史写法：场景在条带后面，只清条带区以免整屏黑闪），**条带区外的页面元素没人清**；游戏自身的恢复又只重画自己的场景（如俄罗斯方块棋盘 x≥50）→ 残影留下。

**修法（`main.c` `GameSettings_Update`）**：用 `static uint8_t s_page_open` 记录"**上一帧**是否在显示设置页"（★ 本帧点"返回"时 `s_settings_mode` 已经被清成 `NONE`，只能用上一帧状态判断；条带压在设置页上时也要置 1），据此分两条路：

- **从设置页返回** → **整屏清一次**（`LCD_Fill(0,0,LCD_W,LCD_H, g_menu_clear_color)`）+ 交给游戏**整幅**恢复
- **只退出二级菜单**（场景本来就在条带后面）→ 保持"只清条带区"，避免整屏黑闪

★ **整屏清之后必须要求游戏整幅重画**（局部恢复会缺一块）：

| 模式 | 整幅恢复调用 |
|---|---|
| 2048 / 华容道 / 大鱼吃小鱼 | `*_full_redraw()` + `*_update()`（够用） |
| 俄罗斯方块 | `tetris_menu_mark_dirty()` + `tetris_menu_bg_redraw()`（棋盘+侧栏，区外本来就是黑底） |
| **推箱子** | **新增 `sokoban_menu_settings_restore_full()`** |

- 推箱子为什么特殊：地图**会跨到条带区上方**（`g_oy = 20 + (200 - rows*tile)/2`，从 y≈20 起就有图），旧的局部恢复 `sokoban_menu_settings_restore()` 只重画 `y >= VIDEO_MENU_Y` 的格子 → 整屏清过之后上半张地图会空掉
- `sokoban_menu_settings_restore_full()` = `s_menu_visible=1` + `sokoban_draw_level(当前关)`（内含整屏清屏）+ 按钮面板 + 关卡编号

> 通用教训：**"清哪块屏"要和"页面/菜单实际画到哪"匹配**——整屏绘制的页面必须整屏恢复；覆盖条式（底部条带）的菜单才能只清条带区。

## 32. 推箱子按钮图：中英两套 + 外部 Flash 固定保留区（2026-09）

需求：推箱子底部三个按钮（上一关 / 重新开始 / 下一关）要按语言换图，英文模式用英文版按钮。

### 32.1 为什么不能两套都放字库资源

- 按钮图 30×31 RGB565（小端）= **1860 B/张**，两套 6 张 = **11,160 B**；
  而字库固件（`FLASH_DATA_STORE_MODE`）只剩 **460 B** ? —— **要烧进外部 Flash 的数据，必须先躺在字库固件的内部 Flash 里**（外部 Flash 挂在 SPI 上、不在 SWD 总线上，PC 改不了它）。
- 曾考虑"字库固件分中/英两版、各烧一次"：被跳过的资源会和相邻资源**共用 4KB 扇区**，而 `FlashStore_BurnAll()` 是"写前擦除"→ 擦邻居的扇区就会把跳过那套图的边缘擦掉 ?（要么读-改-写那一扇区，要么做 4KB 对齐填充，都太绕）。

### 32.2 采用方案：英文那套单独占一块固定保留区（不走资源表）

- 中文那套**不动**：仍是资源表里的 ID 71~73（`FLASH_STORE_ID_IMG_PREV/NEXT/RESTART`），换新图只需重烧字库
- 英文那套放在外部 Flash 的固定地址 **`BTN_IMG_EN_ADDR = 0x00600000`**（4KB 对齐，视频区 0~2.87M 与字库区 约8.19M 之间的空闲区），布局 `[prev_en][next_en][restart_en]`，每张 1860 B
  - ★ 不进资源表 = **不动目录/不动布局** → 加这套图**不需要重烧字库**，也不用担心扇区共用
  - ★ 以后视频大幅变长或字库区变大时，要重新确认这块没被占用（宏在 `flash_store.h`）
- 烧写用**独立烧录模式 `BTN_IMG_STORE_MODE`**（`config.h`，仿 `VIDEO_CHUNK_STORE_MODE`）：写两块 —— ① 英文按钮图 5580 B（2 个扇区）② 菜单游戏名字模 864 B（见 §33）—— 各自 CRC 回读校验；两块都不碰字库资源区/目录，所以**不用重烧字库** ?
  - 数据源：① `sok_img_prev.c` 的 `const uint8_t g_btn_img_en[5580]`（**已是小端字节成品**，直接按字节烧；由 `gen_btn_blob.py` 生成）② `chinese_fonts.c` 的 `const uint8_t g_menu_glyph_ext[864]`
  - ★ 字模块的地址**不能写死**：`BtnImgStore_BurnAll()` 先 `FlashStore_ResInit()` 读出目录头里的 `data_start`，再算 `(data_start & ~4095) - MENU_GLYPH_SIZE`（和运行期 `FlashStore_MenuGlyphRead()` 用同一套算法）
  - 字库资源总量一变（`data_start` 移动）**就必须重烧步骤 2**，否则字模块会压到/被压
- 运行期取图：`sokoban.c` 的 `sok_btn_img_rows(which, vis_rows, src_w)`
  - 中文 → `sok_load_img_rows(FLASH_STORE_ID_IMG_*)`（原路径，走资源目录）
  - 英文 → `FlashStore_RawRead(BTN_IMG_EN_ADDR + off, ...)`（按绝对地址读，新增 API）
  - `which`: 0=上一关 1=下一关 2=重新开始；整图绘制与裁剪绘制都走这一个函数（老的三条 `sok_*_draw()` 不再被引用，会被 `--gc-sections` 回收）
- 按钮图格式（两套一致）：**源图 30×30 + 第 31 行纯黑（画的时候不透明，用于盖住底边）**；绘制固定 **2 倍放大** → 屏上 60×62；`0x0000` 在 0~29 行当透明跳过

### 32.3 烧录流程（★ 加/换按钮图时按这个顺序）

| 步骤 | config.h 宏 | 内容 | 说明 |
|---|---|---|---|
| 0 | （只在改了字模时） | `gen_latin2.py` 重生成 `chinese_fonts.c/.h` | LATIN24 是资源表里的一项 → 改了必须重烧步骤 1 |
| 1 | `FLASH_DATA_STORE_MODE` | 字库/图片全量（含**新中文按钮图**、拉丁字模） | 资源表项数没变 → 老板子也只重烧这一份 |
| 2 | `BTN_IMG_STORE_MODE` | 英文按钮图 5580B + 菜单游戏名字模 864B | 不碰字库，可单独重烧 |
| 3 | （都不开）= 游戏模式 | 游戏固件 | 切语言时按 `g_language_index` 选图/选字 |

- 只烧步骤 3 也能跑：中文按钮仍是旧图、英文按钮显示空白、菜单 4 行游戏名不出字（保留区没烧）——**要看到新图/新字必须烧 1、2**
- ★ **烧完步骤 1 要等 MCU 自己搬完再烧步骤 3**：复位后它把内部 Flash 的数据写进外部 Flash，写完才置 `g_res_prog`（magic `RES1`，6 个字：magic/total/index/pct/crc_fail/**result**）。用 `riscv-none-embed-nm` 取符号地址后轮询 `mdw`，**`result != 0` 且 `crc_fail == 0` 才算成功**；不等就烧步骤 3，会出现"字库烧了一半"的怪现象（某个字模还是旧的，用户会说"改了没效果"）
- 占用（2026-09 实测）：字库固件 64,964 B（316 B 余量）；游戏固件 64,096 B（1,184 B 余量）；按钮图烧录固件约 14 KB（比 §32 初版多带 864B 字模数组）

## 33. 下滑菜单"游戏名"中文化：追加字模放"字库数据区紧前面"（2026-09）

需求：主菜单/下滑菜单那 5 行里的游戏名改成中文 —— 2048→**方块合并**、俄罗斯方块→**方块消行**、华容道→**华容道**、大鱼吃小鱼→**大鱼小鱼**；英文模式对应 `Merge / Tetris / Klotski / Big Fish`。

### 33.1 为什么这 12 个汉字不能走原来那两条路

- 12 个字 = 12 × 72B = **864 B**，而字库固件（`FLASH_DATA_STORE_MODE`）当时只剩 **460 B**（§32 时期）?
- 放进资源表（`s_resources[]`）→ 资源项 +12 会让目录变大、`data_start` 前移，**每次加字都要重算布局**；而且字模数组仍然要占字库固件的内部 Flash（还是放不下）?
- 所以走第三条路：字模数组**仍编在固件里**（`const uint8_t g_menu_glyph_ext[864]`，只有 `BTN_IMG_STORE_MODE` 那个小固件带得动），由**烧录模式单独写到外部 Flash** —— 不进资源表、不动目录，**加字不需要重烧字库**

### 33.2 放在哪：字库数据区紧前面的那一小块

```c
addr = (data_start & ~4095) - MENU_GLYPH_SIZE      /* MENU_GLYPH_SIZE = 12 * 72 = 864 */
```

- `data_start` = 资源数据区起点（存在目录头里，运行期由 `FlashStore_ResInit()` 读入 `s_data_start`），它落在**某个 4KB 扇区的内部**，从该扇区起到芯片末尾才是"全量烧字库"的擦除范围
- 向下取整到 4KB 再减 864B → 落在**那个扇区起点之前**：既是字库擦除范围之外（烧字库擦不掉它），又紧贴字库区（满足"字库还是放在一个区"）
- ★ 地址**必须现算**（`flash_store_glyph_addr_from()`），不许写死 —— 字库资源总量一变、`data_start` 一动，这块就要重烧
- 接口：游戏模式 `FlashStore_MenuGlyphRead(buf)` 读 864B 进菜单字模缓存；烧录模式 `BtnImgStore_BurnAll()` 擦/写/CRC 校验（与英文按钮图同一趟，见 §32.3 步骤 2）
- 没烧过时这片内容是 `0xFF` → 只是那几行不出字，其它功能不受影响

### 33.3 菜单侧：虚 ID + 槽位换算

- `chinese_fonts.h`：`MENU_EXT_ID_BASE = 128`、`MENU_EXT_CNT = 12`，12 个字各占一个**虚 ID**（128 起；资源 ID 最大 127，不会冲突）
  - **顺序不能改**（`g_menu_glyph_ext` 里字节的排列就是它）：方 块 消 行 | 华 容 道 | 鱼 大 小 | 合 并。加字只能往后追加
  - 这里的"鱼"是用户单独给的"大鱼小鱼"里的鱼，**不是**主菜单那个 `font_yu`
  - ★ 用户给的是**点阵数据本身**（不是字形描述），只能按字节贴进 `g_menu_glyph_ext`，不能用 `gen_font*.py` 重生成
- `menu.c`：`MENU_FONT_SLOTS 24 → 36`；`MENU_FONT_SLOT(id)` 里 `id >= MENU_EXT_ID_BASE` → 槽位 `24 + (id - 128)`
- `s_row_text[]` 这 4 行改成文字行（`MENU_ROW_2048` 也并进"文字行"那个 case 分支，不再走 `draw_2048_strip()`）：

| 行 | 中文（字模 ID 表） | 英文 |
|---|---|---|
| `MENU_ROW_2048` | 方块合并 | `Merge` |
| `MENU_ROW_TETRIS` | 方块消行 | `Tetris` |
| `MENU_ROW_KLOTSKI` | 华容道 | `Klotski` |
| `MENU_ROW_FISH` | 大鱼小鱼 | `Big Fish` |

- **同时删掉的**：`draw_2048_strip()`、`s_menu_digits[4*64]`、`s_dig_2048[4]`，以及 T 图标 / 4×4 网格 / `font_yu` 三个图标绘制分支（不再被引用，留着会被 `--gc-sections` 回收）

### 33.4 拉丁侧的连带改动

- `MENU_WORDS` 加 `Tetris / Klotski / Big Fish / Merge` → LATIN24 由 26 字扩到 **29 字**（补上 **T / K / M**），1248B → **1392B**
- 缺 **T**/**K** 时的现象是"某行整体不居中"（不是报错，见 §29.1）；**M** 在 14px 下必须手工点阵（见 §29.2）
- ★ LATIN24 是**资源表里的一项** → 改完必须**重烧字库**（§32.3 步骤 1）；而 §33.2 那块字模改了只需重烧步骤 2

## 34. 低电图标闪烁拖慢全局帧率：主循环里的"每帧阻塞式写屏"（2026-09，已修）

**症状**：改用外部电源（没装电池）后，用户反馈"菜单上/下滑动画变慢、俄罗斯方块按住加速下落也慢"，但**视频播放正常**、方块**自动下落也不慢**。

**根因**：没装电池 → 电池 ADC 读到接近 0 → 电量档位 `BAT_LEVEL_0` → `Main_FlashLowBattery()` 持续跑（灭 2s / 亮 1s），而**亮屏段里每帧都重画一次低电图标**：

```c
} else {
    LCD_ShowLowBatteryOverlay();   /* ← 每帧 */
    g_lowbatt_showing = 1;
}
```

- 低电图标是 5/8 屏宽的大电池框（150×82）+ 凸起 + 感叹号，一次 overlay = **7 次填充、约 2.2K 像素**
- 而 `LCD_Fill()` 是**纯 CPU 逐像素阻塞写**（`LCD_WR_DATA_16Bit` 循环，无 DMA）
- 60fps 下每秒白白吃掉约 **36ms** 帧时间

**为什么只慢这几处**：

| 现象 | 原因 |
|---|---|
| 菜单滑动、方块软降变慢 | 都是"**每帧固定位移**"（2px/帧、1 格/帧），帧时间被吃 → 每秒位移变少 |
| 视频正常 | DMA 解码 + 直传，不吃主循环帧时间 |
| 自动下落不慢 | 按 `GetTimerCount()` **微秒累积**，与帧率无关 |
| 中英文都慢 | 与菜单文字无关（当时刚做完 §33 游戏名中文化，容易误判成它） |

**修法（两处）**：

1. `Main_FlashLowBattery()`（`main.c`）：亮段里**不再每帧重画**，加 `LOWBATT_OVERLAY_REDRAW_US = 100ms` 节流，刚进亮段时立即画一次
   - ★ `g_lowbatt_showing` **仍要每帧维持为 1** —— 菜单条带渲染靠它调 `lmbat_strip()` 把电池行画进条带；只有"纯游戏画面"才依赖这里补画
   - 游戏画面只在状态变化时才重绘，100ms（约 6 帧）补一次足够；开销从"每秒 60 次"降到"每秒 10 次"
2. `LCD_DrawLowBatteryOverlay()`（`display.c`）：7 次 `LCD_Fill` → **`LCD_Fill_DMA`**（画和清都走这个函数，所以亮段/灭段一起变快）。DMA 版与菜单条带共用 `shared_buffer`，本函数只在主循环里串行调用，不冲突

**教训（与"触摸 I2C 每帧多读 32B 导致全局动画慢两成"同类）**：

- ★ **主循环里"每帧做一次阻塞式写屏"是隐藏的帧时间杀手**：单次看着只有一两毫秒，乘 60 帧/秒就是几十毫秒的预算
- 排查手法：先分清哪些动画"**按帧计速度**"（会变慢）、哪些"**按时间计**"（不受影响）——前者变慢就说明帧时间被吃了
- 修法优先级：先**降频率**（不必要时别画），再考虑换 DMA —— 换 DMA 只省掉 CPU 环节，传输时间仍受 SPI 时钟限制

## 35. 英文菜单"看着比中文慢"：菜单框每帧重绘里的重复填充（2026-09，已修）

**症状**：同一台机器上，英文菜单（上/下滑、二级菜单）的滑动速度看着比中文慢一点，"区别不大，但能感觉出来"。

**根因**：`menu_draw_nrow_frame_only()` 逐扫描行画菜单框，"文字框"分支里的**青色底是重复填的**：

```c
for (x = mb; x < mw - mb; x++) { 青底 }        /* ← 内饰行已经整行刷过青了 */
...
else {
    for (x = txt_l; x <= txt_r; x++) { 青底 }   /* ← 又按"文字区宽度"刷一遍, 白写 */
    for (x = txt_l; x < blu_l; x++) { 蓝框 }
    for (x = blu_r + 1; x <= txt_r; x++) { 蓝框 }
}
```

- `txt_l..txt_r` 一定落在 `mb..mw-mb` 内部（`txt_l = (mw-txt_span)/2 - PAD`，`txt_r = txt_l + txt_span + 2*PAD - 1`；各尺寸菜单都是 `mw=150` / `mb=5`），**所以这一遍完全白写**
- 每帧要跑约 190 个扫描行 × `(txt_span + 20)` 次（中文 116、**英文 132**）
- ★ **这才是中英差异的来源**：`TXT_SPAN_EN = 112`（英文最长 "Big Fish" = 8 字 × 14）比 `TXT_SPAN = 96` 宽 16，白写的量也跟着每行多 16 —— 单看只有 1% 量级，但菜单重绘本身已经吃掉大半帧预算（5 行菜单每帧要重发 150×230×2B ≈ **69KB**），踩在临界点上就被放大成"能感觉到的差异"

**修法**：删掉那一遍青色填充，`else` 分支只画左右两条蓝竖框 → 中英这段开销**完全相等**，每帧还省约 1.5–2 ms

**同期附带修的一处**（`menu_blit_en_row()` 位循环）：
- 字模只有 14 列宽 → 第 2 字节低 2 位恒 0，只扫高 6 位
- 整字节为 0 直接 `continue`（空格、窄字母 i/l 常整字节空，原来白跑 8 次位判断）
- 英文一行 33 个字符，位判断次数从固定 16 次/字符降下来

**教训**：

- ★ **"整片填色 + 再覆盖一部分"是常见重复劳动**：只要覆盖范围包含在整片范围内，就应该直接分区间写，而不是先写满再盖
- 查**两套布局（中/英、分辨率）的性能差异**时，先看"哪些循环的长度依赖那两套不同的常量"（这里是 `txt_span`），比盯着字体绘制本身更容易找到真凶
- 与 §34 同源：菜单滑动这类"每帧全量重绘"的场景，单点开销看着都很小，但每帧预算本来就紧（69KB/帧的 SPI 发送 ≈ 9ms），几毫秒的浪费直接决定掉不掉帧

## 36. 低电灭段恢复（续）：tetris/fish 的设置模式分支 + 鱼的擦除方式（2026-09，已修）

### 36.1 俄罗斯方块/鱼缺 `g_settings_from_game` 分支

**症状**：进游戏后上划菜单点"设置"（**二级设置条带**），低电图标灭段时**电池位置黑一下**；2048/华容道/推箱子不会。

**根因**：二级条带只盖住电池主体（x=45~195），**条带外的凸点（x=195~210）必须由游戏自己恢复**。2048（`d2048.c` 506 行）/华容道/推箱子在 `*_lowbatt_restore()` 里都有 `g_settings_from_game` 分支只重绘凸点，**俄罗斯方块和鱼没有**：
- 俄罗斯方块掉进"纯游戏"分支 → `g_board_dirty = 3; draw_board()` **整棋盘重绘** → "先画棋盘再画条带"，明显闪一帧
- 鱼掉进"菜单"分支 → **把游戏菜单画到设置条带上**

**修法**：
- `tetris_lowbatt_restore()` 加 `else if (g_settings_from_game) { draw_preview(); }`（凸点跨在右侧预览区上，重绘预览即可覆盖）
- `fish_clear_lowbattery()` 开头加 `if (g_settings_from_game) { …只恢复电池区… return; }`

### 36.2 鱼的恢复不能"整块填背景"

**症状**：鱼在灭段时"**电池框内部黑一下**"（一片纯色），**偶尔**出现。

**根因**：鱼的场景是"**纯色背景 + 精灵实体**"。原来的 `clear_entity_rect(lb_dims, 0, 127, 120)` 会把电池矩形 **166×83 整块**填成背景色，再逐个重绘相交的鱼/玩家 —— 而重绘要 `FlashStore_ResLoad()` **从外部 Flash 流式读精灵图**，这期间框内是**空的**；框内鱼越多越明显（所以是"有时候"）。

**修法**：**只擦图标自己画上去的那几条线**，不动框内：

```c
static void fish_erase_lowbatt_icon(void) {     /* 用背景色擦 7 条窄带 */
    LCD_Fill_DMA(45,  79, 195,  81, COLOR_BG);   /* 上边(2px) */
    LCD_Fill_DMA(45, 159, 195, 161, COLOR_BG);   /* 下边 */
    LCD_Fill_DMA(45,  79,  47, 161, COLOR_BG);   /* 左边 */
    LCD_Fill_DMA(193, 79, 195, 161, COLOR_BG);   /* 右边 */
    LCD_Fill_DMA(195, 104, 210, 136, COLOR_BG);  /* 右凸点 */
    LCD_Fill_DMA(111, 92, 129, 128, COLOR_BG);   /* 感叹号竖条 */
    LCD_Fill_DMA(111, 137, 129, 155, COLOR_BG);  /* 感叹号点 */
}
```

再 `redraw_entities_in_rect(lb_dims, 0, 127, 120)` 把正好压在这些线上的鱼/玩家补回来（**不填背景**）。

- 为此把 `clear_entity_rect()` 拆成"填背景 + `redraw_entities_in_rect()`"，后者单独复用
- 三条恢复路径（设置模式 / 一级菜单 / 纯游戏）都改成 `fish_erase_lowbatt_icon() + redraw_entities_in_rect(...)`
- 一级菜单分支里原来还先 `LCD_ClearLowBatteryOverlay()`（把线条刷成**黑色**）再填背景 —— **那一步删掉了**（多出一段纯黑显示时间），相关填充也一并改用 `LCD_Fill_DMA`

**教训**：

- ★ **低电灭段恢复要"只恢复被图标盖住的东西"**：图标是"细线条 + 凸点"，就不该整块填背景 ——"擦干净图标"和"把整片填成背景"是两件事
- ★ **"填背景 + 重绘实体"看着稳妥，但重绘实体往往很贵**（从外部 Flash 流式读图/逐像素画），**"填"和"画完"之间那段时间就是空的一块** → 表现为闪；框里东西越多越明显
- 用背景色**直接擦掉图标线条**（每条带几百像素）比整块填（13.8K 像素）快一个数量级
- 判断"谁的恢复没做对"：**先看各游戏 `*_lowbatt_restore()` 的分支是否齐**（设置模式 / 退出菜单 / 重开菜单 / 纯游戏 / 结束态），缺哪个分支就会掉进不该走的那条

## 37. 待机/唤醒健壮性：三个"等用户动作"的循环 + 触摸IC复位时机（2026-09，已修）

### 37.1 `Touch_WaitWakeInputsReleased()` 的"等松手"循环会卡死

**症状**：进游戏 → 点一下唤醒 → **再一直按住屏幕** → 到息屏时间后**背光黑了但设备不进待机，松手才睡**。

**根因**：待机流程里 `Enter_Standby()` 会调用 `Touch_WaitWakeInputsReleased()`"等手指松开"：

```c
while (stable_count < 20) {          /* 连续100ms判定为已释放 */
    ...
    if (touch_released && INT == Bit_SET) stable_count++;
    else stable_count = 0;           /* ← 用户按着 → 永远是 0 */
    IWDG_ReloadCounter();            /* ← 一直在喂狗, 看门狗也不会来救 */
    Delay_Ms(5);
}
```

用户按着 → 循环**永不退出**；而背光在更早的 `GameAutoSleep_Enter()` 开头就已经关了 → 看起来是"黑了却不睡"。

**为什么"休眠时手指就一直按着"反而正常？** 因为那条路走的是**触摸唤醒**，唤醒流程里 `Touch_WakeResumeInit()` 会**复位一次 IC** → IC 回到刚启动的状态、不主动产生点报告 → INT 回到高电平 → 循环第一次判断即视为"已释放"。

**修法**：`Touch_WaitWakeInputsReleased()` **开头补一次同样的复位**（IT7259: 低 100us；CST816S: 低 10ms），两种 IC 都做。

**踩过的弯路**：先给它加了"1 秒放弃"兜底 —— **错的**。那样用户还按着就进待机，IC 的后续点报告会立刻把设备唤醒（现象：刚睡就醒）。

### 37.2 CST816S 的判据要单独放宽

CST816S 配的是 `0xFA=0x40`（**周期产生中断**），按住期间 INT 会周期性拉低 → 拿 `INT == Bit_SET` 当"是否释放"的旁证会把计数反复清零。故 **CST816S 只看手指数寄存器**，不掺 INT；IT7259 的 INT 只在有事件时拉低，可作旁证，保持不变。

### 37.3 两个"隔离"分支会绕过休眠检查

唤醒后的触摸隔离有两处，**都是"连续2帧读到松开才解除"、都没有上限**，而且都在函数里 `return 1` 提前退出，**把后面的休眠超时检查整段跳过**：

| 位置 | 变量 | 症状 |
|---|---|---|
| `Main_HandleTouchInput()` | `s_wake_wait_release` | 唤醒后触摸被永久屏蔽 |
| `GameAutoSleep_AfterTouch()` | `s_game_wait_release` | 游戏里"按住不动也要休眠"失效 |

**修法**：两处都加约 1 秒上限（60 帧），到点无条件解除。

### 37.4 唤醒路径不要重复复位 IC

`Touch_Init()` 里的复位（IT7259 低 100us）在**中断已使能之后**执行时，`Delay_Us` 是 SysTick 忙等、**会被中断打断** → 偶发冲过 1ms → **芯片进 sleep（0.1uA，彻底停机、点屏幕也唤不醒）**。

**修法**：新增 `s_wake_resumed` 标记，`Touch_WakeResumeInit()` 置 1 → 唤醒流程里那次 `Touch_Init()` **只把 RST 保持高电平、不再拉低**（复位已经在"中断还没使能"的早期做过一次）。上电路径和故障自愈路径仍然是完整复位。

### 37.5 I2C 连续读失败要能自愈

`Touch_IsPressed()` 原来在 `IT7259_ReadPoint()` 失败时只 `return 0`（"保持原状态"），**一旦通信坏掉就坏到底**。现在连续失败约 2 秒会自动重跑 `Touch_Init()`。

### 37.6 休眠判定的"手指在动"要用死区

`GameAutoSleep_AfterTouch()` 里原用**逐像素比较**判断"手指动过"：

```c
if (ts.x != s_last_x || ts.y != s_last_y) s_game_last_activity_us = now;
```

而触摸 IC 的静止死区只滤 ±1 → 长按时 **±2px 抖动就被当成"手指在动"** → 计时器每帧刷新 → **长按永不休眠**。改成 **3px 死区**（`GAME_SLEEP_MOVE_DEADZONE`）。

- ★ 这个死区**只用于"要不要刷新休眠计时器"，不修改任何坐标** —— 所以菜单拖动/下滑的跟手精度（1px）不受影响。改完要能回答"它会不会影响手感"，答案是"它连坐标都没碰"

**通用教训**：

- ★★ **"等一个用户动作"的循环必须有上限**：等松手、等抬起、等确认 —— 用户不配合就会永久卡住；更隐蔽的是循环里还在 `IWDG_ReloadCounter()`，**看门狗也不会来救**
- ★★ **隔离/门控逻辑里的"提前 return"会跳过它后面的所有检查**（这里是休眠超时）。加门控时要想清楚"被跳过的还有什么"
- ★ **触摸 IC 的"复位"是个状态开关**：复位后它回到刚启动状态、不主动上报 —— 这个特性既能治"卡在等松手"，也能（反向）造成"INT 不再动作"的睡死
- ★ IT7259 的 RST 低脉冲**必须 <1ms**；忙等延时会被中断打断，所以**复位尽量放在中断还没使能的早期**做
- ★ 修"卡死类"问题别急着加超时：**先看同样的操作在别的路径上为什么能正常** —— 差异点往往就是答案（这里是"唤醒时复位过 IC"）

## 38. 【待做】推箱子"撤回上一步"（2026-09 评估完，等 Flash 有余量再做）

### 38.1 为什么这个功能逻辑上极便宜

推箱子的状态全在 `g_runtime_map[256]`（1 字节/格，玩家/箱子就地写在地图里），而且：

1. **"这格本来是目标点还是空地"不用额外存** —— `g_level_bcd[128]`（原始地图）+ `is_orig_target(row,col)`（`sokoban.c:121-126`）已经常驻 RAM，随时能反查
2. **一次移动最多只推 1 个箱子**（`sokoban_move()` 里发现前面还有箱子就直接拒绝）
3. **玩家位置随时能扫出来**（`sokoban_find_player()`，`sokoban.c:440-452`）

于是 **每步只需记录 1 字节**：低 2 位 = 方向（与 `SokobanDir` 枚举同序），第 3 位 = "这步推了箱子吗"。

**撤回时全部靠反推**：设当前玩家格为 `cur`、记录的方向为 `dir`，则

- 上一步玩家格 = `cur - dir`
- 被推箱子的新位置 = `cur + dir`，**原位置 = `cur`**

### 38.2 撤回的执行（与 `sokoban_move()` 完全对称）

落格时统一用 `is_orig_target()` 决定写 `TARGET` 还是 `FLOOR`：

```
（推了箱子时）g_runtime_map[cur+dir]  ← 箱子离开      → TARGET/FLOOR
（推了箱子时）g_runtime_map[cur]      ← 箱子回到这里  → BOX_ON_TARGET/BOX
              g_runtime_map[cur]      ← 没推箱=玩家离开 → TARGET/FLOOR
              g_runtime_map[cur-dir]  ← 玩家回来      → PLAYER_ON_TARGET/PLAYER
重绘 cur-dir / cur / (cur+dir) 这 2~3 格（复用 sokoban_draw_cell_at）
```

### 38.3 历史栈的行为（用户要求"可持续撤回"）

- 每次**成功**移动 → `push(dir | pushed<<2)`；每次撤回 → `top--` 并执行逆操作
- **可连续撤回**，直到栈空（`top == 0` 时静默不响应）
- **栈满（64 步）后继续走** → **丢掉最旧的一条**（整体前移一格），保证"永远能撤最近 64 步"
- **撤回后又走新的一步** → 新记录直接覆盖栈顶（被撤回的"未来"作废，不分叉）
- **换关 / 重开** → 清空栈（在 `sokoban_prepare_level()` 里 `top = 0`，那里本来就是复位点）
- **通关后撤回** → 需一并清掉通关状态与大字（`s_won` / `sok_win_draw`），或干脆通关后禁用撤回（待定）

**RAM 开销**：64 步 × 1 字节 = **64 字节**（RAM 还剩 2,508 B，完全不是问题）

### 38.4 触发方式（待定）

推箱子现有交互已排满：拖动=移动（50px 阈值）、底部上划=按钮面板（上一关/重开/下一关）、顶部下滑=退出菜单、按钮面板二次上划=设置。且按钮面板那 3 个按钮是 60×60、x=15/90/165，**刚好占满整行，塞不下第 4 个**。

## 39. 合并 2048/华容道的数字绘制 + 修"格子旁不消失的白点"（2026-09）

> 背景：为给推箱子"撤回上一步"（§38）腾 Flash 空间做的第二轮瘦身。

### 39.1 先看这条：瘦身的方法论修正

第一轮瘦身（把"删死代码"当收益）只省了 32 B，教训有三条：

- ★★ **`.map` 里能搜到符号 ≠ 占 Flash**：`is_menu_visible` 那几个函数确实在 map 里，但位置在 `Discarded input sections` 段（在 `Memory Configuration` **之前**），本来就被链接器丢了。**判断真实占用必须看 `Memory Configuration` 之后的段**。
- ★★ **合并小函数（<40 B）会丢掉内联机会**，估算要打对折甚至更低。真正有收益的是**大块、逐行同构**的重复代码。
- ★ 每合并一项都要**重新编译量 `.text`**，不能只靠估算。

**有效的判据**：两份实现"**框架逐行相同、只有常量/规则参数不同**" → 有戏；"结构相似但每行都不同" → 别碰（比如低电灭段恢复的 5 个分支，看着像，其实是各自的画面逻辑）。

### 39.2 合并 `draw_tile_number`（实测省 148 B）

`d2048.c` 与 `klotski.c` 各有一份约 40 行的"格子内居中画数字"：

```
val==0 返回 → uint_to_digits 分解 → LCD_CS_CLR → 二选一的字号分支 → 逐位居中绘制 → LCD_CS_SET
```

差异只有三处，全部参数化到 `menu.c` 的 `game_grid_draw_number()`：

| 差异点 | 参数 |
|---|---|
| 字号档位阈值（2048：4 位以上才缩放；华容道：3 位以上） | `big_first` |
| 取色（2048 按 `val<=32` 取黑/白；华容道恒白） | `text_color` |
| `dc==2` 时的字间距（2048 固定 16；华容道 `(tile_size-16)/2`） | 由 `big_first` 分支 |

各游戏只留一个薄 wrapper（保留各自的取色规则）。**实测 64,840 → 64,692 B**。

### 39.3 修"格子旁边不消失的小白点"

**现象**：2048 玩几轮后，**曾经放过数字的格子**旁边出现一个小白点，**不会自己消失**；数字本身显示正常。

**根因**：`draw_tile_bg` 里

```c
LCD_Fill(x, y, x + TILE_SIZE - 1, y + TILE_SIZE - 1, color);
```

而 **`LCD_Fill` 的 `end` 参数是"不含"的**（内部是 `for (j = xsta; j < xend; j++)`）—— 可由 `display.c:67` 画"上边"时传 `g.by + 1` 正好是 1 行高来反证。所以这句实际只填 **`x ~ x+38`**，**格子的最右列 `x+39` 从来没被清过**。

而 3 位数（如 512）的最后一位正好画到 `tx+24 ~ tx+39`，**它的最右列就落在 `x+39`**。数字消失后格子内部被新背景盖住，只有那一列的墨迹留下 —— 就是那个白点。这也解释了三个特征：**只有放过数字的格子有**（3 位数才顶到右边界）、**滑动几次才出现**、**不会消失**（那一列没人重绘）。

**修法**：传 `x + TILE_SIZE`（不含语义下正好填满 40 列）。2048 与华容道同样处理。

**?? 但不要因此把全项目改一遍**：扫描发现 `LCD_Fill` 传 `-1` 的调用有 **43 处**，其中大多数是**画边框/格线/装饰条**——那里的"少 1 像素"是**有意为之**（改了会让线变粗、位置偏移）。**只有"用来反复擦除某块区域"的调用才是隐患**。

### 39.4 本节教训

- ★★ **`LCD_Fill(…, xend, …)` 的 `xend` 不含**：**擦区域要传 `x + w`，画线才传 `x + w - 1`**。项目里两种写法混用，改之前先判断那处是"擦"还是"画"
- ★ **"残留类"bug 的通用排查法**：问"这块区域**平时谁负责重绘**" —— 如果答案是"没人"，那它一旦被画上东西就永久留在那儿
- ★ 定位这类问题**先收集现象特征**（何时出现 / 会不会自己消失 / 哪些格子有）—— 用户这三个回答直接把范围缩到了"数字绘制 + 右边界"

## 40. 游戏模式不再编入内部 16x32 数字字模（2026-09，实测省 656 B）

> 目的：给 §38 推箱子"撤回上一步"腾 Flash。

### 40.1 找到的东西

`sok_img_win.c` 的 `const uint8_t font_digits[640]`（16x32 数字字模）看起来必须留，实际是**烧录模式专用的备份**：

- 运行期真正用的是**外部 Flash 里的 `FLASH_STORE_ID_DIGITS`**（`FlashStore_ResLoad`）
- 内部这份只被两处 `if (!data) data = &font_digits[...]` 引用（`sok_draw_digit_16x32`、`sok_draw_digit_scaled`），注释写得很清楚：**"烧录模式下回退内部 Flash"**
- 而 `flash_store.c` 的资源表里 `{ font_digits, 640 }`（= 要烧出去的那份源数据）**整表在 `#ifdef FLASH_DATA_STORE_MODE` 里** → **游戏固件里这个数组没有任何真实用途**

### 40.2 做法

两条回退加条件编译，只有烧录模式才回退内部数组；游戏模式改成"取不到就不画"：

```c
#if defined(FLASH_DATA_STORE_MODE) || defined(VIDEO_CHUNK_STORE_MODE) || defined(BTN_IMG_STORE_MODE)
    if (!data) data = &font_digits[digit * FONT_DIGIT_BYTES];   /* 烧录模式: 进度百分比要能显示 */
#else
    if (!data) return;                                          /* 游戏模式: 目录无效则整屏资源都没有 */
#endif
```

数组本身仍留在 `sok_img_win.c`（烧录固件用），游戏固件里因为没人引用 → `--gc-sections` 回收。

### 40.3 实测

**64,692 → 64,036 B（省 656 B = 数组 640 + 代码 16）**，余量 **588 → 1,244 B**。

用 §39.1 的判据复核：`SPI_LCD.map` 里 `.rodata.font_digits 0x280` 现在位于 **`Memory Configuration` 之前**（即 `Discarded input sections`）→ 确认不再占 Flash。

顺带验证过烧录模式没被编坏：对 `sok_img_win.c` 单文件分别用 `FLASH_DATA_STORE_MODE` / `VIDEO_CHUNK_STORE_MODE` / `BTN_IMG_STORE_MODE` 各编一遍，全部 exit 0。

### 40.4 教训

- ★★ **"同一个东西在固件里有两份来源"是找空间的高价值线索**：一旦发现某资源既有内部数组又有外部 Flash 版本，先查内部那份是不是**只给烧录模式当回退** —— 是的话一个 `#if` 就能整块回收（本次一次就顶上好几轮"合并小函数"）
- ★ **资源表（`s_resources[]`）里的条目 ≠ 运行期要用**：表内 `font_digits` 的存在不代表游戏固件需要它；判断依据是"**游戏模式下有没有真实引用**"（看 map 里该段落在 `Memory Configuration` 前还是后）
- ★ **改了条件编译要顺手验一下被 `#if` 排除的那些模式**：用同一套 `-I`/`-march` 参数对单文件 `-D<宏>` 各编一次即可，不必切 `config.h`（切了会把游戏固件覆盖掉）
- ★ **行为差异要写清楚**：现在"外部 Flash 资源目录无效（整块没烧过）"时数字不再回退、直接不画。这种板子上中文/图片本来就没有（全来自外部 Flash），差别只是"整屏空白" vs "只剩数字"，故可接受

## 41. 推箱子三级菜单（撤销/设置/返回）+ 撤销/重做（2026-09）

### 41.1 交互参数（反复调过好几轮，接手别再从头摸）

- **起手上划位置三处统一**：`SOK_SWIPE_Y = 230` —— 只认屏幕最底那条窄带（y>230）起手；距离统一 `MENU_SWIPE_TRIGGER_DIST`（5px）。涉及：游戏内上划出导航按钮组 / 一级面板上划出二级菜单 / 撤销界面上划回二级菜单

### 41.5 本节教训

- ★ **commit message 的编码**：用编辑工具新建 `.txt` 写提交信息会按系统 ANSI 存 → git 报 `commit message did not conform to UTF-8`、日志乱码。正确做法：用 PowerShell `[IO.File]::WriteAllText(path, msg, New-Object System.Text.UTF8Encoding($false))` 写，再 `git commit --amend -F <file>`

## 42. 低电图标与二级菜单共存 + 按钮区划动作废（2026-09，Flash 已满）

### 42.1 电池灭段恢复的裁剪规则（sokoban）

- **按"当前面板上缘"裁剪重绘范围**：只补面板没盖到的那部分，面板盖住的区域**不要重绘瓦片** —— 面板不透明且每帧都会重画自己；先补瓦片再由面板盖回来会"闪一帧"（面板是分条带从上往下 DMA 的，被盖住的部分会先露出来）
- **凸点/右边框那一列（x=195~210）永远在菜单框（x≤195）之外**，任何状态都要单独补一次 `sok_redraw_battery_tiles(195, 79, 210, 161)`
- **二级菜单停靠位 = `RESTART_MENU_Y - 1`（=79）**：电池图标居中算出 `by=79`，上边框占第 79、80 两行，菜单框从 80 起会漏出第 79 行（一条黑线）。停靠位上移 1px 正好盖掉；`sok_panel_drag_start` 里 kind==1 的 `s_panel_rest`、`sok_lvl2_clear_frame` 的清屏起点必须用同一个值，否则菜单会整体跳 1px
- ★ **`s_menu_slide_y` 必须在"面板收起 / 从设置返回"时复位**：`sok_lvl2_clear_frame`、`sokoban_menu_settings_restore`、`sokoban_menu_settings_restore_full` 三处都置 `SOK_BTN_Y`。它同时被"电池恢复裁剪"当上缘用，留着二级菜单的旧值 79 → 电池区下半整片留黑（现象：从设置返回后图标熄灭，电池下面一块黑）

### 42.2 按钮区划动作废手势（不连跳、不点击、不复活）

- 需求：在"上一关/重新开始/下一关"按钮区域划动时，不触发长按连跳、松手也不点击；**划出去再划回来也不能复活**
- 做法（都在 `sokoban_update` 的按钮面板分支）：
  - 复用已有的"二次上划"块：把 `s_swipe_origin_y > SOK_SWIPE_Y` 从外层条件挪进内层，先判"底部窄带 → 二级菜单"，否则 `up_move > MENU_SWIPE_COMMIT_DIST`（20px，复用现有常量）→ `s_drag_btn = 4`（**4 = 非 0~3 的作废标记**）+ 清 `s_hold_button`/`s_hold_us` + `return`
  - **必须同时清长按计时**：按下瞬间就锁定 `s_hold_button` 且之后不再重扫触摸，只作废命中不停计时的话 1 秒后照样连跳（用户实测："短按不会，长按还是会复活"）
  - **不复活**：`sokoban_hold_update` 里重新命中那行加守卫 `if (s_drag_btn != 4) s_drag_btn = sok_btn_hit_test(...)`。`s_drag_btn` 一直是 4 → 松手既不进 1/2/3 分支、也不进"点空白关面板"分支 = 纯取消
- 覆盖范围：向上划 √；向下划仍是原有"下滑>5px 关闭面板"（松手不点击），按住期间的长按未作废（未做，需要更多空间）

### 42.3 空间现状与教训

- ★ **Flash 已用满：65,280 / 65,280（余 0 B）**：再改前先腾空间（§39 那条"数字绘制三合一"估省 200~400B）
